# 数据库驱动接口（第二轮：写路径）

> Status: Approved
> Owner: OpsKat 维护者
> Last updated: 2026-10-16

**Objective:** 「SQL 数据库」资产的全部写操作——表格编辑、建表、改表、删表、清空表、新建数据库、导入、导出为 SQL 语句、复制为 SQL 语句——的方言 SQL 都由驱动生成，前端只发结构化意图；共享代码（前端与后端）不再有任何按驱动名的分支。

**Hard invariant:** 除「有意的行为变化」一节列出的各项外，四个内置驱动（MySQL、PostgreSQL、SQL Server、SQLite）的写操作不回退：同样的操作在预览中给出的语句文本、执行结果、报错位置与改动前一致；第一轮交付的读路径行为不变；已保存的资产配置不需要迁移。

## 所处位置

本规格是 issue #329（Oracle 数据库支持）三步路线第一步「宿主驱动接口」的第二轮。第一轮（读路径，规格 [2026-10-10-database-driver-seam](2026-10-10-database-driver-seam.md)）已随 PR #342 合并。**[用户决定]** 第一轮规定写路径留到本轮，过渡期内未迁移的文件列在豁免名单里、只减不增。本轮结束后豁免名单清空，下一步「扩展平台能力」做的扩展驱动只需实现驱动接口，就能拿到完整的读写功能。

## Problem

标注：**[已核实]** = 对照 opskat main（`45e1d7ea`）源码确认；**[用户决定]** = 本轮对话中用户选定；**[未复现]** = 读代码得出、尚未在运行中复现。

1. **写路径的方言 SQL 仍由前端拼接。** [已核实] 前端有 10 个文件仍按驱动名分支，被列在豁免名单里（`frontend/eslint.config.js:42-53`）：表格编辑（`TableDataTab.tsx`、`lib/tableEdit.ts`）、建表 / 改表 / 删表 / 清空（`lib/tableSql.ts`、`AlterTableDialog.tsx`、`DatabaseTree.tsx`）、建库（`CreateDatabaseDialog.tsx`）、导入（`ImportTableDataDialog.tsx`、`lib/tableImport.ts`）、导出与复制为 SQL（`ExportTableDataDialog.tsx`、`lib/tableExport.ts`）。后端的导入批处理按驱动发不同的关闭外键检查语句（`internal/service/query_svc/table_import.go:176`），是后端豁免名单里的唯一一项（`internal/archtest/driver_branch_test.go:17-20`）。由扩展提供的驱动无法把方言知识编进前端。
2. **导入批处理经一座取原始连接的过渡桥执行。** [已核实] `ExecuteTableImport`（`internal/app/query/query_ops.go:262`）经 `getOrDialPanelSQLDB`（`:60`）拿到驱动底层的 `*sql.DB`；扩展驱动的连接在扩展内部，宿主拿不到。
3. **改表对话框加载列信息时自己拼读 SQL。** [已核实] `AlterTableDialog.tsx:106-233` 按驱动各写一段查系统表的 SQL 经 `ExecuteSQL` 执行，是第一轮遗留的读路径。
4. **导入时，需要整批执行的三种选项全部报错。** [已核实] 导入对话框在 `window.go.app.App.ExecuteTableImport` 找绑定（`ImportTableDataDialog.tsx:202-205`），而绑定实际挂在 `window.go.query.Query` 下，`app` 这一层根本不存在。所以「复制」模式、取消「出错继续」、勾选「忽略外键」这三种需要整批执行的导入一律报 `ExecuteTableImport binding unavailable`。单测 mock 的也是这条错路径（`ImportTableDataDialog.test.tsx:17-25`），所以测试没有发现。另外，请求里从不带目标表（`Tables`），即使绑定找得到，SQL Server 的「忽略外键」也不起作用。
5. **字面量只转义单引号。** [已核实] 前端 `sqlQuote`（`lib/tableSql.ts:3`）对所有驱动都只把 `'` 写成 `''`：
   - SQL Server 的文本没有 `N` 前缀，[未复现] 推断 Unicode 列中写入的非本代码页字符会变成 `?`；
   - MySQL 在默认的 `sql_mode` 下把反斜杠当转义符，[未复现] 推断含 `\` 的值写入后会被改掉；
   - 导入把二进制写成 `X'…'`（`lib/tableImport.ts:493-510`），这不是合法的 T-SQL，SQL Server 要求 `0x…`。
6. **只有 MySQL 认得自增列。** [已核实] 只有 MySQL 从 `Extra` 读出 auto_increment（`internal/dbdriver/sqldb/table.go:304`），SQL Server 的 IDENTITY 列和 PostgreSQL 的 `GENERATED … AS IDENTITY` 列都被当成「非空且无默认值」（`internal/dbdriver/mssql/table.go:38-50`）。于是：
   - 在表格里新增一行时，这些列被要求必填（`lib/tableEdit.ts:25-30`），但在 SQL Server 上填了值又会被拒绝。
   - SQL Server 导入只能靠一段运行时判断自增列的包装，并且自增列在映射里、但不是匹配键时，追加/更新仍报 `Cannot update identity column`（第一轮规格「有意的行为变化」第 7 项记录的已知限制）。
7. **PostgreSQL 改表对话框加载不到列，改名会写进 schema 前缀。** [已核实] 加载列时 schema 写死为 `public`，并拿 `schema.table` 去匹配 `table_name`（`AlterTableDialog.tsx:120`），而 PostgreSQL 的表名统一以 `schema.table` 形式传入，所以一列也查不到。改名输入框预填的是 `schema.table`（`:84`）：PostgreSQL 会生成 `RENAME TO "public.x"`，SQL Server 的 `sp_rename` 会把表真的命名为 `dbo.x`（`lib/tableSql.ts:140-145`）。按 `.` 拆分表名（`quoteQualifiedIdent`，`lib/tableSql.ts:16`）也让名字里带点的表在导出、复制、导入时引用出错。
8. **表格编辑提交后，失败的修改也被清掉。** [已核实] 只要有一条语句影响了行，就清空全部待提交的修改与新增行（`TableDataTab.tsx:685-688`），失败的那几条也在其中，用户无从重试。
9. **MySQL 改列会悄悄丢失列属性。** [已核实] 改列名、类型、可空、默认值或注释时，`CHANGE COLUMN` / `MODIFY COLUMN` 只按这五项重建列定义（`lib/tableSql.ts:91-107,241-244`）：
   - 列原有的 `AUTO_INCREMENT`、`ON UPDATE CURRENT_TIMESTAMP`、字符集与排序规则全部丢失。例如只给自增主键加一条注释，它就不再自增。
   - 未改动的表达式默认值（如 `(uuid())`）会被重新加上引号，变成字符串默认值。

## Actors and user stories

1. 作为**运维用户**，我想让四种内置数据库的表格编辑、建表、改表、删表、清空、建库、导入、导出与复制为 SQL 在这次改动后用起来和以前一样，预览里看到的就是将要执行的语句。
2. 作为**运维用户**，我想让 SQL Server 的中文、MySQL 的反斜杠、二进制、自增列这些值写进去就是我给的值，改表不要动我没改的列属性，导入的每个选项都能用。
3. 作为**驱动实现者**（宿主维护者，以及下一步的扩展作者），我想只在驱动里实现写操作的语句生成与批量执行，就让一种数据库获得全部写功能，而不必改查询面板或导入导出的共享代码。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | **[用户决定]** 写操作按「生成 → 预览 → 执行」进行：前端发结构化意图，驱动在自己的会话上生成方言语句并返回；前端在现有的预览 / 确认对话框里展示；确认后执行的正是展示的那些语句 | 预览即执行，预览界面几乎不变；保留 UPDATE / DELETE 的确认步骤。Rejected: 驱动收到意图直接执行，预览另走一次「只生成」——预览与执行各生成一次，中间表结构变了就会不一致 |
| 2 | **[用户决定]** 本轮除了迁移，还修 Problem 4–9；读回值的编码问题（二进制与超过 2^53 的整数读回前端时已失真）另开一轮 | 4–9 的修复点正好落在迁移要改的生成代码上，修正就是让驱动生成正确的方言。Rejected: 纯迁移——驱动要刻意复刻错误写法（如不加 `N` 前缀）；连读回值一起修——要改读路径值的编码，表格显示、导出、复制都受影响，回归面最大 |
| 3 | 单条语句继续走现有的通用执行；导入中需要整批执行的情形（复制模式、出错即回滚、关闭外键检查），改为驱动提供的「在一条连接上执行一批语句」操作，取代经过渡桥取原始连接 | [已核实] 外键检查开关在 MySQL 是会话级的，必须与语句同连接；扩展驱动的连接只有驱动自己拿得到（第一轮决定 4）。Rejected: 宿主继续经桥取 `*sql.DB`——扩展驱动无法提供 |
| 4 | 语句生成是会话上的操作：驱动可以先查表的元数据（列类型、自增列、主键），再决定写法 | 正确的字面量与自增处理都依赖列信息：SQL Server 是否加 `N` 前缀看列类型，是否打开自增写入看映射里有没有自增列。Rejected: 纯函数式生成、只靠前端传来的类型串——前端的类型串不全（SQL Server 不带长度、拿不到自增），也会把方言知识推回前端 |
| 5 | 导入中「读懂源文件」的部分留在前端：文件解析、日期格式、小数点符号、空值策略、二进制的 hex / base64 解码。列属于数字、日期、日期时间、二进制还是文本，由驱动按自己的类型系统判断，随表元数据告诉前端 | 这些是源文件格式的知识，与目标数据库无关；类型归类是方言知识（如 SQL Server 的 `image`、`smalldatetime`）。Rejected: 文件解析整体搬到后端——与方言无关的大量代码要用 Go 重写，没有收益 |
| 6 | 驱动不起作用的选项不显示：没有「关闭外键检查」能力的驱动，导入不显示「忽略外键」；建库对话框只显示驱动声明的选项字段及其默认值 | 沿用第一轮决定 5（未声明的功能入口隐藏）。[已核实] PostgreSQL 勾选「忽略外键」不起任何作用（`ImportTableDataDialog.tsx:501`）；SQL Server 建库的字符集字段被忽略（`CreateDatabaseDialog.tsx:56-58`）。Rejected: 显示但无效果——误导用户 |
| 7 | **[用户决定]** 自增列在新增行与导入中不再必填；用户给了值就原样写入，没给就由数据库生成 | 与第一轮「有意的行为变化」第 7 项（SQL Server 导入写入自增列）一致，MySQL / SQLite 现在就是这样。Rejected: 新增行里自增列不可填——与导入、与 MySQL 现状不一致 |
| 8 | **[用户决定]** 修复 MySQL 改列丢失列属性（Problem 9） | 改表的生成本来就要搬进驱动，修复的增量成本小；当前缺陷会静默改坏表结构。Rejected: 记为已知问题——留着一个会悄悄改表的缺陷 |
| 9 | 豁免名单清空后删除名单本身，按驱动名分支的检查对共享代码无例外 | 第一轮决定 11 的终点。Rejected: 保留空名单——留着以后再加例外的口子 |

## 写操作的流程

所有写操作遵循同一流程：

- 前提：资产的驱动声明了该写功能。动作：用户在界面上完成编辑或填写对话框，点「预览 SQL」或「提交 / 确定」。结果：前端把结构化意图（见下表）交给后端，驱动生成语句返回；预览对话框展示这些语句，确认后逐条执行的正是这些语句。四个内置驱动生成的语句文本与改动前一致，「有意的行为变化」列出的除外。
- 前提：同上。动作：生成失败（如表已不存在、意图里的列名不在表中）。结果：错误显示在原来显示错误的位置，不打开预览，也不执行任何语句。
- 前提：资产的驱动没有声明某写功能。结果：入口不显示（同第一轮）；若仍被调用，返回「该驱动不支持此操作」，且不执行任何语句。
- 前端共享代码与后端共享代码都不出现按驱动名的判断，豁免名单不再存在。

| 写操作 | 前端发出的意图 | 驱动负责的部分 |
|---|---|---|
| 表格编辑 | 每个被改的行：原值（用于定位）、改动的列与新值；新增行：填写过的列与值；要删除的行 | 表引用、字面量、有主键时按主键定位，无主键时的单行定位写法（`LIMIT 1` / `TOP (1)` / `ctid` / `rowid`），空行插入写法，自增列写入 |
| 建表 | 表名、各列的名称 / 类型文本 / 可空 / 默认值 | 表引用、引号、默认值的写法 |
| 改表 | 原表名与新表名（不带 schema）、表注释、各列的增删改（名称、类型、可空、默认值、注释） | 各库的改表语法（含 SQL Server 的 `sp_rename`、SQLite 的限制），哪些属性可改（界面据此锁定输入），MySQL 改列时保留未改动的列属性 |
| 删表 / 清空 | 目标表（可跨库多选） | 删表与清空的语句（SQLite 清空发 `DELETE FROM`） |
| 新建数据库 | 库名与驱动声明的选项值 | 选项字段与默认值的声明、建库语句 |
| 导入 | 映射后的行（已按源文件格式转换好的值：文本、空值、二进制字节）、目标列、匹配键、导入模式、是否合并成多行插入与单条上限、是否出错继续、是否忽略外键 | 每种模式的写法（upsert / 跳过 / 复制前清空），字面量，自增列写入，关闭与恢复外键检查，整批在一条连接上执行与回滚 |
| 导出为 SQL | 列与行（当前页，或整表流式读取的每一块） | `INSERT` 语句的表引用与字面量 |
| 复制为 SQL | 选中的列与行、主键 | `INSERT` / `UPDATE` 语句（`UPDATE` 仍只取第一行） |

## 表格编辑

- 前提：表格里有修改、新增与删除。动作：提交。结果：与改动前一样，先插入、再更新，每条语句单独执行，不包事务。执行后，**只有成功的修改与新增行**被清掉并刷新数据；失败或影响 0 行的修改留在表格里，可以修正后重新提交。错误与「未匹配到行」的提示与改动前一致。（有意的行为变化第 4 项）
- 前提：表没有主键。结果：界面是否显示「无主键（将使用全列匹配）」提示，由驱动报告它能否精确定位单行决定，不再按驱动名判断：PostgreSQL（`ctid`）与 SQLite（`rowid`）能精确定位，不显示；MySQL 与 SQL Server 显示。删除预览中的无主键警告不变。（有意的行为变化第 8 项）
- 前提：新增一行。结果：驱动报告的自增列（MySQL `AUTO_INCREMENT`、SQL Server `IDENTITY`、PostgreSQL `GENERATED … AS IDENTITY` 与 `serial`）不要求填写。用户填了值则按该值写入：SQL Server 生成的语句临时打开该表的 `IDENTITY_INSERT`、执行后关闭（出错也关闭）；PostgreSQL 的 `GENERATED ALWAYS` 列带 `OVERRIDING SYSTEM VALUE`。（有意的行为变化第 2 项）

## 建表、改表、删表、清空、建库

- 建表：对话框的字段不变；语句由驱动生成，与改动前一致。
- 改表：
  - 打开对话框时，表的列、类型、可空、默认值、注释和表注释都由驱动读取，不再由前端拼查询。PostgreSQL 任一 schema 的表都能加载出全部列。（有意的行为变化第 3 项）
  - 改名输入框只给不带 schema 的表名，改名后表仍在原 schema。（有意的行为变化第 3 项）
  - 哪些属性能改由驱动声明，界面据此锁定输入。四个内置驱动的锁定范围与改动前一致：SQLite 的已有列只能改名或删除；SQL Server 的已有列不能改默认值，也不能改注释。
  - MySQL 改列时，用户没动的列属性（自增、`ON UPDATE`、字符集、排序规则、表达式默认值）原样保留。（有意的行为变化第 5 项）
  - 多条语句时按顺序执行，遇错即停，与改动前一致。
- 删表 / 清空：确认对话框的内容与按库分别执行的方式不变，语句由驱动生成。
- 新建数据库：对话框只显示驱动声明的选项字段，默认值由驱动给出：
  - MySQL：字符集 `utf8mb4`、排序规则 `utf8mb4_0900_ai_ci`；
  - PostgreSQL：编码 `UTF8`、排序规则 `en_US.UTF-8`；
  - SQL Server：只有排序规则（默认空），不再显示不起作用的字符集字段（有意的行为变化第 7 项）；
  - SQLite 仍不显示新建数据库。
  - 选项值的合法字符校验与改动前一致。

## 导入

- 前提：在导入向导中完成映射与模式选择。结果：摘要步骤展示驱动生成的前 8 条语句（与改动前同样位置、同样截断）。值的转换（日期、小数点、空值策略、二进制编码）规则不变，列属于哪一类由驱动判断。
- 前提：选「复制」模式、或取消「出错继续」、或勾选「忽略外键」。动作：开始导入。结果：整批语句由驱动在一条连接上执行。复制模式和不继续的情形放在一个事务里，出错即回滚并在日志中注明；勾选「忽略外键」时，导入前关闭外键检查、结束后恢复（出错也恢复），SQL Server 作用于导入的目标表。完成后显示新增 / 更新 / 删除 / 错误计数。三种情形都不再报 `binding unavailable`。（有意的行为变化第 1 项）
- 前提：其余情形（出错继续且不忽略外键、非复制模式）。结果：与改动前一样逐条执行，逐条更新进度，可以取消。
- 自增列：
  - 映射包含自增列时，源文件里的值原样写入：SQL Server 打开 `IDENTITY_INSERT`（出错也关闭），PostgreSQL `GENERATED ALWAYS` 列带 `OVERRIDING SYSTEM VALUE`。
  - 「更新」与「追加/更新」不去改数据库不允许更新的自增列（SQL Server `IDENTITY`、PostgreSQL `GENERATED ALWAYS`）：已有行的其余列照常更新，自增列保持原值。第一轮记录的 `Cannot update identity column` 不再出现。
  - SQL Server 预览只在映射包含自增列时带开关自增写入的语句，不再给所有表都套运行时判断。（有意的行为变化第 2、6 项）
- 「忽略外键」只在驱动声明了关闭外键检查的能力时显示；PostgreSQL 不声明，不再显示这个原本不起作用的选项。（有意的行为变化第 6 项）
- 失败：数据库的错误原样写进导入日志并弹出提示，与改动前一致；整批执行时连接或事务本身出错，同样显示在日志里。

## 导出为 SQL 与复制为 SQL

- 前提：导出格式选 SQL，或在表格右键选「复制为 INSERT / UPDATE」。结果：语句由驱动生成；行的范围（当前页 / 整表流式）、每行一条 `INSERT`、`UPDATE` 只取第一行、写文件与写剪贴板的方式都与改动前一致；字面量见下一节。表名带点的表正确引用。

## 字面量与表引用

所有写操作生成的语句中，字面量与表引用都由驱动按自己的方言给出（有意的行为变化第 2、3 项）：

- **SQL Server**：
  - 写入 Unicode 文本列（`nchar` / `nvarchar` / `ntext`）以及用这些列定位行时，文本带 `N` 前缀，中文等字符原样写入；其他类型的列不加前缀。
  - 二进制写成 `0x…`。
- **MySQL**：文本中的反斜杠按会话的 `sql_mode` 转义；在 `NO_BACKSLASH_ESCAPES` 模式下不转义。写入后读回的值与用户给出的一致。
- **PostgreSQL**：二进制写成 `'\x…'::bytea`。
- **SQLite**：二进制写成 `X'…'`。
- **表引用**：库、schema 与表名分开传给驱动，不再按 `.` 拆分字符串。数值、日期、空值等其余字面量的写法与改动前一致。

## 有意的行为变化

1. **导入整批执行的三种情形可用。** 前提：任一驱动，选「复制」模式、或取消「出错继续」、或勾选「忽略外键」（PostgreSQL 见第 6 项）。动作：开始导入。结果：按「导入」一节执行，不再报 `ExecuteTableImport binding unavailable`；SQL Server 勾选「忽略外键」时，导入期间目标表的外键约束确实停用、结束后重新启用。[已核实] 改动前这三种情形必定报错。
2. **SQL Server 与 MySQL 的文本、各驱动的二进制、自增列按方言正确写入。** 前提：表格编辑、导入、导出或复制为 SQL 涉及 SQL Server 的 Unicode 文本列、MySQL 中含反斜杠的文本、SQL Server 的二进制列，或任一驱动的自增列。结果：按「字面量与表引用」与「表格编辑」「导入」两节的规则生成；写入后读回的值与用户给出的一致；新增行不再要求填写自增列。[未复现] 文本与反斜杠的损坏是读代码推断的，动手前先在真库上复现，以确认这是修复而非行为不变；[已核实] 自增列在 SQL Server / PostgreSQL 上被要求必填（`lib/tableEdit.ts:25-30` 与 Problem 6）。
3. **PostgreSQL 改表可用，改名不带 schema，名字带点的表可正确引用。** 前提：PostgreSQL 任一 schema 的表，或 SQL Server 的表，或名字里带点的表。动作：打开改表对话框并改名，或对带点的表导出、复制、导入。结果：列全部加载；改名后的表名就是用户输入的名字，仍在原 schema；带点的表名作为一个整体引用。
4. **表格编辑提交后保留失败的修改。** 前提：一次提交里部分语句成功、部分失败或影响 0 行。结果：成功的修改被清掉并刷新，失败的留在表格里。[已核实] 改动前全部清掉。
5. **MySQL 改列保留未改动的属性。** 前提：MySQL 表中带 `AUTO_INCREMENT`、`ON UPDATE CURRENT_TIMESTAMP`、列级字符集 / 排序规则或表达式默认值的列。动作：在改表对话框里只改它的名称、类型、可空、默认值、注释中的一部分。结果：生成的语句保留用户没改的属性；执行后用「查看建表语句」看到这些属性仍在。[已核实] 改动前这些属性会丢失（Problem 9）。
6. **导入预览与选项按驱动能力呈现。** 结果：
   - SQL Server 导入预览只在映射包含自增列时出现开关自增写入的语句（第一轮第 7 项曾说明所有 SQL Server 表都带运行时判断的包装）。
   - PostgreSQL 的导入不再显示「忽略外键」。
   - 「更新」与「追加/更新」不再试图改写不可更新的自增列，第一轮第 7 项记录的已知限制解除。
7. **SQL Server 建库对话框不再显示字符集字段。** 改动前该字段的值被忽略。
8. **SQLite 无主键的表不再显示「无主键」提示。** 前提：SQLite 中没有主键的表。结果：表格工具栏不显示该提示，因为 SQLite 按 `rowid` 精确定位单行，与 PostgreSQL 现在的处理一致。删除预览中的无主键警告不变。

## 兼容性

- 已保存的资产配置不变、不迁移。
- 通用的 `ExecuteSQL` 与 SQL 编辑器执行保持不变；新增的写路径调用是增量。导入批处理的绑定换成经驱动执行，前端改为调用实际存在的绑定。
- 驱动功能声明的集合不变（第一轮已声明写功能）。新增的只是写功能内部的细项声明，四个内置驱动按今天的实际情况声明，「有意的行为变化」第 6、7 项除外：
  - 能否关闭外键检查；
  - 建库的选项字段；
  - 改表时可改的属性；
  - 能否不靠主键精确定位单行。
- 不改变 SQL 权限策略、审批与审计；AI 与 opsctl 的 SQL 执行不涉及本轮。

## Out of scope

- 读回值的编码：二进制与超过 2^53 的整数在读回前端时已失真，用它们定位行会定位不到或定位错——另开一轮（**[用户决定]**）。
- 表格编辑、改表的多条语句包事务、失败整体回滚——新功能，另行提出。
- 建表对话框新增主键、自增、索引、注释等字段；改表支持索引与主键——新功能，另行提出。
- 删除数据库——现在没有这个功能。
- 默认值输入的表达式识别规则（如 SQL Server 的 `getdate()` 被当成字符串加引号）——保持改动前的规则，另行提出。
- 手动提交 / 回滚与固定会话、扩展向「SQL 数据库」注册驱动、Oracle 驱动——第二步与第三步规格。
