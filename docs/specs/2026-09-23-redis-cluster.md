# Redis 集群与哨兵支持

> Status: Approved
> Owner: OpsKat maintainers
> Last updated: 2026-09-23

**Objective:** Redis 资产除单机外支持 Redis Cluster 与 Redis Sentinel 两种部署模式。桌面端的连接、浏览、编辑、概览，AI `exec`，以及 opsctl（`exec` / `batch` / `create` / `update asset`）在三种模式下都能正确访问数据；表单尽量自动识别部署模式、哨兵组名和不可直连的节点。

**Hard invariant:** 已有单机 Redis 资产的配置、连接行为、库选择、审批 / 策略匹配与审计均不变。集群模式下，只覆盖部分节点的结果必须明示「只覆盖了部分节点」，不能冒充全量。明文密钥（数据节点密码、哨兵密码）不写入日志、审计或导出文件。

## Problem

1. **只能连单机。** 所有路径都用 `redis.NewClient` 建立单节点客户端（`internal/connpool/redis.go:31`），没有集群 / 哨兵配置，也没有这两种客户端。（已验证：代码阅读）
2. **SSH 隧道把所有连接都送到种子地址。** `tunnelDialFunc` 忽略 go-redis 传入的目标地址，固定连 `NewSSHTunnel(host, port)` 的 target（`internal/connpool/dialer.go:19-23`、`internal/connpool/tunnel.go:40-60`）。集群自动发现的节点、哨兵返回的主节点地址都会被错连到种子主机。（已验证：代码阅读）
3. **集群里不带 key 的命令只落在一个随机主节点。** go-redis 对没有 key 的命令取随机 slot（`go-redis/v9@v9.7.3/osscluster.go:1841-1846`），`SCAN` / `KEYS` / `DBSIZE` / `INFO` / `FLUSHDB` 等只反映约 1/N 的数据且不报任何异常。现有 key 浏览依赖单节点 `SCAN`（`internal/service/redis_svc/service.go:252`），库计数依赖 `INFO keyspace`（同文件 `:244`）。（已验证：源码阅读）
4. **多库假设遍布各处。** `database` 字段、AI `scope`（`internal/ai/helper/redis_helper.go:50`）、底栏库选择器（`RedisKeyBrowser.tsx:62`）、建 key 对话框都默认有多个库；集群只有 db0。（已验证：代码阅读）
5. **多 key 操作跨 slot 会失败。** 批量删除一次 `DEL` 多个 key（`internal/service/redis_svc/mutations.go`），在集群下 key 分布在不同 slot 时返回 `CROSSSLOT`。（已验证：代码阅读 + 真机 `MGET user:1 user:2` 返回 CROSSSLOT）
6. **AI 连接缓存不区分库。** `RedisClientCache` 只按资产 ID 缓存（`internal/ai/helper/conn_cache.go:62`），同一轮对话里对同一资产用两个不同 `scope` 时，第二次会复用第一次那个库的连接。本轮要把 `scope` 扩展成「库或节点」，属于同一单元内的根因修正。（已验证：代码阅读）

## Actors and user stories

1. 作为**运维工程师**，我想把生产 Redis 集群或哨兵组作为一个资产添加（只填一个地址即可），然后像单机一样浏览、编辑 key、查看节点状态。
2. 作为**运维工程师**，我想在节点挂掉或主从切换后仍能继续使用；连不上的部分要明确告诉我，而不是给出不完整的列表。
3. 作为**调用 opsctl 的外部 AI agent**，我想对集群执行命令时，带 key 的命令自动路由；不带 key 的命令在没指定节点时明确失败并告诉我有哪些主节点，以免把局部结果当成全量。
4. 作为**内置 AI**，同样的规则通过 `exec` 的 `scope` 参数生效。

## Design decisions

| # | 决策 | 依据与被否方案 |
|---|---|---|
| 1 | 三种模式（单机 / 集群 / 哨兵）同一轮交付（用户决定） | 生产上哨兵部署常见；哨兵模式的浏览器与单机相同，拨号与地址映射的改造和集群共用。被否：先做集群、哨兵留到下一轮 |
| 2 | 不单独支持「主从」模式 | 主从中的任一节点本身就是单机 Redis，现有单机模式能直接连；复制信息在完整 INFO 里已可见。被否：新增主从模式 —— 没有额外能力 |
| 3 | 集群里不带 key 的命令必须指定节点，少数与节点无关的命令例外（用户决定） | 避免局部结果冒充全量（Problem 3）。被否：随机节点并标注来源 —— 局部结果问题仍在；自动汇总所有主节点 —— 每条命令都要定义合并语义，`SCAN` 游标难以合并 |
| 4 | 节点指定沿用现有 `scope` 概念：单机 / 哨兵时 `scope` 是库号，集群时是节点地址 `host:port`。opsctl 新增 `--scope` 与之对应 | AI 已有 `scope` 参数，一个概念覆盖两种含义，接口最窄。被否：新增 `node` 参数 —— 与 `scope` 并存会造成两个参数互斥的组合 |
| 5 | 节点地址映射本轮就做（用户决定），同时作用于集群节点和哨兵返回的地址 | 节点宣告的地址是内网 / Docker 网桥 IP 且本机不能直连时，不配映射就用不了。两种模式都在同一层拨号，统一处理不增加成本。被否：只给集群做 —— 哨兵在 Docker 部署时会遇到同样的问题 |
| 6 | 隧道 / 代理 / 代理链一律按 go-redis 请求的目标地址拨号（先做地址映射） | 修 Problem 2 的根因。单机模式的目标地址就是配置的地址，行为不变。被否：为每个节点单独配隧道 —— 节点是自动发现的，无法预先配置 |
| 7 | 自动识别放在表单里显式触发（测试连接 / 读取组名），不在保存时静默改配置 | 用户能看到并确认每一项被识别出的值。被否：保存时自动切换模式 —— 会静默改掉用户填的东西 |
| 8 | 哨兵密码只支持直接输入（加密保存），不接托管凭据 | 哨兵密码是独立于数据节点的第二个密钥，托管凭据选择器目前一个资产只绑定一个。被否：再加一个凭据选择 —— 表单和凭据关联模型都要扩展，超出本轮 |

## 部署模式与连接配置

Redis 资产新增「部署模式」，取值单机 / 集群 / 哨兵。已有资产没有这个字段，按单机处理，行为与现在完全相同。

- **单机**：字段与现在相同（主机、端口、用户名、密码 / 托管凭据、数据库）。
- **集群**：填「种子节点」，每行一个 `host:port`，至少一行；另有用户名、密码 / 托管凭据，所有节点共用。不显示数据库字段，固定 db0，并有一行说明。只填一个种子节点就能发现整个集群；多填几个是为了第一个节点不可达时仍能连上。
- **哨兵**：填「哨兵节点」（每行一个 `host:port`，至少一行）、「主节点名称」（必填）、数据节点的用户名、密码 / 托管凭据、数据库；另有一块可选的「哨兵认证」（哨兵用户名、哨兵密码），只在哨兵本身设了密码时才需要填。
- 隧道（跳板机 / SOCKS5 / 代理链）与 TLS 配置对三种模式都生效，作用于每一条节点连接，包括自动发现的节点和哨兵返回的主节点。
- 「高级」分组在集群和哨兵模式下多一个「节点地址映射」：每行 `宣告地址 = 实际地址`。拨号前如果目标地址命中左侧，就改连右侧。格式错误或同一个宣告地址出现两次时，禁止保存并指出是哪一行。
- 校验：模式对应的必填项缺失时，禁止保存与测试，并给出与现有 `formMissingHost` 同类的提示。

切换部署模式时，已填的其它模式字段保留在表单里但不保存。保存时只写入当前模式用到的字段。

## 自动识别

所有识别都走一次真实连接，复用表单当前的认证、隧道、TLS 配置；失败时只显示错误，不改动任何字段。

1. **部署模式**：单机模式下测试连接成功后，如果目标节点的 `redis_mode` 是 cluster 或 sentinel，在主机 / 端口下方显示提示：「检测到这是 Redis 集群节点」（或哨兵节点），并附一个切换按钮。点击后切到对应模式，把当前 `host:port` 作为第一个种子节点 / 哨兵节点，然后按对应模式执行后续识别。不点就保持单机，允许保存。
2. **哨兵组名**：哨兵节点填好后（输入框失焦、或点「从哨兵读取」），读取哨兵监控的组。只有一个组且主节点名称为空时直接填入；有多个时在主节点名称下方列出，每项显示组名、当前主节点地址和从节点数，选中后填入；主节点名称仍可手动输入。
3. **补全哨兵节点**：读到组名后，如果该组还有未填的哨兵，在哨兵节点下方提示「从哨兵发现另外 N 个节点：…」和「补全」按钮，点击后追加到列表。
4. **哨兵认证提示**：哨兵返回需要认证时，提示「哨兵需要单独的密码」，并聚焦哨兵认证区。
5. **不可直连的集群节点**：集群模式测试连接时，逐一尝试直连集群宣告的每个节点地址（经配置的隧道 / 代理，并先应用已有映射）。有连不上的，测试结果显示「种子节点可连 · N 个节点不可达」，高级页的地址映射上方列出这些地址，并提供「生成映射」：把尚未映射的地址填到左侧，右侧留空，由用户填写。

测试连接成功时，结果行显示：单机为「连接成功」；集群为「连接成功 · 集群 ok · M 主 R 从」（`cluster_state` 不是 ok 时如实显示）；哨兵为「连接成功 · 当前主节点 host:port」。

## 桌面端浏览器

参照 mockup：`.dev-kit/artifacts/2026-09-23-redis-cluster/mockups/`（本地证据，以下文为准）。

**哨兵模式**的 key 浏览、编辑、库选择、控制台与单机完全相同，所有读写都发往哨兵报告的当前主节点，主从切换后自动改连新主。概览页顶部多一行摘要卡：组名、当前主节点、从节点 / 哨兵数量、quorum；随后是「复制拓扑」表（节点、角色、复制延迟、状态）和「哨兵节点」表；服务器、内存、运行状态面板和完整 INFO 都取自当前主节点。

**集群模式**：

- **key 列表**：默认扫描所有主节点并合并，数量行显示「N 个 Key · 已扫 k/n 主节点」。底栏原库选择器的位置换成「扫描范围」选择：「全部主节点 (总数)」或某一个主节点（各自显示 key 数），只影响列表扫描的范围。分页「加载更多」在各主节点间继续，直到全部扫完。过滤（含精确 key 查询）同样覆盖所有主节点，精确 key 直接按 slot 查询。
- **部分节点不可达**：扫描跳过不可达的主节点，数量行标为「已扫 k/n 主节点」（警示色），列表上方显示「host:port 不可达，该节点上的 Key（slot 范围）未列出」。对落在不可用 slot 上的 key 进行读写时，原样显示 Redis 返回的错误（如 `CLUSTERDOWN`）。
- **key 详情**：标题行多一个标签「slot N · 所在主节点」。读写按 slot 自动路由。
- **写操作**：建 key 对话框不显示库选择。批量删除逐个 key 执行（不再一次 `DEL` 多个 key），部分失败时报告已删除数量与失败的 key。
- **控制台**：带 key 的命令自动路由，多个 key 跨 slot 时原样显示 `CROSSSLOT` 错误。不带 key 的命令发往底栏选中的主节点；底栏为「全部主节点」时报错，提示先在底栏选择一个节点。与节点无关的命令例外（见「命令路由」）。
- **概览**：摘要卡（集群状态、主 / 从数量、slot 覆盖、Key 总数），`cluster_state` 不是 ok 时，状态与 slot 覆盖用错误色，顶栏显示「cluster_state: fail · X 个 slot 不可用」；「集群节点」表每个主节点下挂其从节点，列出地址、节点 ID 前缀、角色、slot 范围、key 数、内存、ops/s、状态，故障节点整行标红并显示原因；服务器 / 内存 / 运行状态面板和完整 INFO 显示顶栏「INFO 节点」选择器选中的节点（默认第一个主节点），自动刷新保持现有行为。不可达的节点，其 key 数、内存显示为「—」，Key 总数显示为「≥ 已知部分之和」。

## 命令路由（AI `exec`、opsctl、桌面控制台共用）

- **单机 / 哨兵**：与现在相同，`scope` 为库号，缺省用资产配置的库；拒绝 `SELECT`。
- **集群**，按顺序判断：
  1. 命令含 key：按 slot 路由到对应主节点。同时给了 `scope` 时忽略 `scope`，结果中注明「按 key 路由到 host:port」。
  2. 与节点无关的命令（`PING`、`ECHO`、`TIME`、`COMMAND …`、`CLUSTER …`）：`scope` 缺省时由任一可用节点执行。
  3. 其余不带 key 的命令：必须用 `scope` 指定节点 `host:port`。缺省时失败，错误信息列出当前所有主节点地址；`scope` 不是集群中的节点，或是一个库号时同样失败并列出主节点。指定的节点可以是从节点（用于只读诊断），由 Redis 决定是否接受。
  4. `SELECT` 一律拒绝，提示集群只有 db0。
- 结果中都注明实际执行的节点地址（集群模式），方便调用方判断覆盖范围。
- AI `exec` 的 `scope` 参数说明与 skill 文档同步写清三种模式的含义。
- AI 的连接缓存按「资产 + 库」区分（修正 Problem 6）；集群模式每个资产一个集群客户端，按节点执行复用其节点连接。

## opsctl

- `opsctl exec <asset> [--scope <db|host:port>] -- <command>`：新增 `--scope`，语义与 AI `scope` 完全一致，仅对 Redis 资产有意义；其它资产类型给出 `--scope` 时报错（退出码 1），不静默忽略。集群缺少节点时退出码 1，stderr 给出主节点列表与 `--scope` 用法。
- `opsctl batch`：JSON 条目支持可选 `scope` 字段，语义同上；位置参数形式 `redis:<asset>:<command>` 不变（无 scope）。
- 审批：审批详情与策略检查中的命令文本不变；审批对话框的详情里显示 `--scope`（如 `opsctl exec cache --scope 10.0.0.1:6379 -- DBSIZE`），让审批人看到命令会发往哪个节点 / 库。已有授权规则按命令文本匹配，不受 `scope` 影响。
- 审计：exec 审计参数记录 `scope`。
- `opsctl create asset --type redis --config` / `update asset`：新增配置字段 `mode`（`standalone` / `cluster` / `sentinel`，缺省为 `standalone`）、`nodes`（集群种子节点或哨兵节点，字符串数组）、`master_name`、`sentinel_username`、`sentinel_password`（仅写入，加密保存）、`node_address_map`（对象：宣告地址 → 实际地址）。校验与桌面表单相同，失败时报出具体字段。单机资产的已有字段与用法不变。
- `opsctl get` / 资产列表的安全视图对集群 / 哨兵资产显示 `mode`、`nodes`、`master_name`，不显示任何密钥。
- opsctl skill 文档（commands.md 等）补充 `--scope` 与三种模式的示例。

## 数据、兼容与安全

- 配置字段只增不改；单机资产无需迁移。
- 哨兵密码与数据节点密码一样加密存储，不回显（详情卡显示掩码）。备份导出 / 导入对哨兵密码与现有 Redis 密码同等处理：导出时按导出选项解密或剥离，导入时重新加密。
- AI `put_asset` 支持与 opsctl 相同的新字段，skill 文档的字段表同步更新。
- 资产详情卡按模式显示：集群为节点列表，哨兵为组名与哨兵节点，地址映射有则显示。
- 日志：连接建立、识别出的模式、不可达节点、主从切换（哨兵报告新主节点）记入结构化日志，不含密钥。

## Out of scope

- 读写分离（从节点读）、按延迟路由。
- 集群运维操作（加减节点、迁移 slot、手动故障转移）的图形界面；仍可通过控制台 / opsctl 执行相应命令。
- 未被前端使用的 `RedisClientList` / `RedisSlowLog` 绑定的集群化。
- 文档站（`../docs`）的用户文档更新，另行处理。
