# AI 对话「停止」一定生效：工具卡住时也能恢复（issue #366 第 4 项）

> Status: Approved
> Owner: OpsKat 维护者
> Last updated: 2026-11-12

**Objective:** 用户点停止（或插话）后，无论这一步卡在什么工具上，对话都会在几秒内回到可继续输入的状态，之后发的消息不会丢；已知会卡住的 SSH 握手、跳板机拨号、本地命令在停止时及时返回。

**Hard invariant:** 工具正常响应停止时（远程命令、SQL、审批等待、模型输出中），停止与插话的表现与现在完全一致；不点停止时，任何工具的执行结果与耗时不变；终端标签页的 SSH 连接（含需要手动输入 MFA 的认证）不受新增超时影响。

## Problem

标注：**[已核实]** = 对照 opskat main `b1210b02`（含 #373、cago-frame/agents `35feba2`）源码或运行确认；**[用户决定]** = 本轮对话中用户选定；**[未知]** = 尚无证据。

issue #366 追加评论：「执行长任务的时候，那条请求回复一直卡在那，后面的请求无法响应，也没办法停止，只能直接终止整个 session。再新启任务的话，又得把整个背景说一遍。」

1. **停止依赖工具自己响应取消。** [已核实] 停止只是取消这一轮的 ctx；cago 在工具阶段无条件等待所有工具返回（`agent/tooldispatch.go` `RunBatch` 的 `wg.Wait()`）才会发出「已停止 / 完成」。任何一个不响应取消的工具都会让这一轮永远收不了尾。模型输出中与审批等待已确认会及时响应取消。
2. **后端放弃等待时不告诉前端，前端无法自救。** [已核实] `StopAIGeneration` 先从运行表中删除这一轮，最多等 3 秒，然后释放资源并返回成功，但不发任何事件。前端只在收到「已停止 / 完成 / 出错」时退出生成中，于是一直显示生成中：再点停止，后端已找不到这一轮，什么都不做；新输入的消息因仍处于生成中而走排队，后端报「没有正在运行的生成」，前端吞掉错误并把这条从队列里删除——消息静默丢失，只能新开会话。后端日志对卡住、放弃等待、排队失败都没有任何记录。
3. **已证实会卡住的工具路径。**
   - [已核实·运行复现] SSH 握手不响应取消：对端接受 TCP 却不回应 SSH 握手时，取消后连接仍无限期等待。沙箱端到端：AI 对这样的资产执行命令，点停止后 76 秒仍在转、再点无效、新消息消失（诊断记录 `.dev-kit/artifacts/2026-11-12-ai-stuck-stop/diagnostics/notes.md`，本地）。经跳板机时最后一跳同理。
   - [已核实·源码] 经跳板机连接下一跳 / 目标时使用不带取消的拨号，取消后要等跳板机自身的连接超时（可达数分钟）。
   - [已核实·源码] 本地命令 `local_bash` 在 Windows 上停止时只结束 shell 进程本身；它启动的子进程（如 `ping -t`、脚本、服务）继承输出管道，cago 在读完输出前不会返回，停止无效。Unix 上若子进程脱离进程组并保留输出管道，同样不返回。
   - [已核实·源码] 本地 kubectl 停止时会结束 kubectl，但若 kubeconfig 配了凭据插件（如等待浏览器登录的 kubelogin），插件继承输出管道，停止后仍等插件退出。
4. **[未知]** 报告者实际命中的是哪条路径（未提供版本、平台、日志；且当前日志不会记录这种卡住）。因此问题 2 的兜底是主修，问题 3 是已知触发源。

## Actors and user stories

1. 作为**让 AI 执行长任务的用户**，我点停止后对话一定会停下来，可以接着说「换个思路」，不必新开会话重讲背景。
2. 作为**在停止收尾期间就开始打字的用户**，我发出的消息不会凭空消失，会在这一轮结束后照常发出。
3. 作为**排查问题的维护者**，我能从日志看出某次停止没能及时收尾、以及排队时这一轮已不在。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | **[用户决定]** 点停止后后端仍给这一轮 3 秒宽限正常收尾；超时则由后端自己发出「已停止」和随后的「完成」，界面表现与正常停止相同：卡住的工具显示「已取消」，回到可输入状态，排队消息照常发出，插话照常生效 | 只有后端知道这一轮是否真的结束，由它保证「停止一定有终态」，前端只有一个状态来源。Rejected: 前端点停止后计时自行复位——后端旧一轮的迟到事件仍会打到新一轮上，两边状态各说各的；Rejected: 额外显示「工具未响应停止，已在后台放弃」说明——用户关心的是对话恢复，多一条文案无助于下一步操作 |
| 2 | 被放弃的那一轮之后产生的任何事件（卡住的工具迟迟返回后的结果、「已停止」「完成」等）一律丢弃，不显示、不影响同一会话后来开始的新一轮 | 否则卡住的工具哪天返回，会把用户已开始的新一轮误判为结束或插入错位内容 |
| 3 | 被放弃的工具在后台继续，直到它自己返回；不强行终止 goroutine | Go 无法从外部终止 goroutine；决定 6–8 让已知路径都能及时返回，剩余未知路径至少不再拖住对话 |
| 4 | **[用户决定]** 生成中排队一条消息、而后端此刻已没有这一轮（如刚点停止正在收尾）时，这条消息留在「等待发送」队列，这一轮结束后与其它排队消息一样照常发出；用户可随时点 × 删除 | 决定 1 保证这一轮一定会结束，留在队列即可不丢。Rejected: 报错并把文字放回输入框——打断用户，且需要重新操作 |
| 5 | 停止宽限超时放弃、以及排队时找不到这一轮，各记一条 warn 日志（含会话 id） | 当前日志对这类卡住完全无记录（问题 2），维护者无从排查 |
| 6 | SSH 握手过程中收到取消（AI 工具、连接池等带取消的调用方）立即中止握手并关闭连接；**不**新增握手超时 | 握手含认证，可能需要用户手动输入 MFA / 键盘交互，固定超时会误伤终端连接。不带取消的调用方（如终端标签页）行为不变 |

## 停止的收尾保证

**前提**：某会话正在生成（模型输出、工具执行或审批等待中的任一阶段）。

**动作**：用户点停止，或对某条排队消息点插话。

**结果**：
- 工具及时响应取消时，与现在一致：这一轮按「已停止」结束，工具显示「已取消」，排队消息照常发出（插话时只发被点的那条）。
- 工具 3 秒内未响应：后端自行结束这一轮，界面在点击后约 3 秒内退出生成中，表现同上；后端记一条 warn 日志。之后这一轮迟到的任何事件都不会出现在界面上，也不会结束或打断同一会话之后开始的新一轮。
- 停止后对话可以继续：新发的消息作为新一轮正常发给模型，模型看到的历史中被中断的工具调用都有对应结果（与现在停止后的历史形态一致）。

**失败**：停止请求本身出错时，沿用现有处理（停止按钮仍在，可再次点击）。

## 停止收尾期间输入的消息

**前提**：界面仍显示生成中（例如刚点停止、后端正在收尾），用户输入一条消息并回车。

**结果**：消息进入「等待发送」队列并保持可见；这一轮结束（无论正常收尾还是决定 1 的超时收尾）后照常发出；后端此时已无这一轮时记一条 warn 日志。不再出现消息静默消失。

## SSH 连接与本地命令响应停止

- **SSH 握手**：AI 对一台「TCP 可连、SSH 不响应」的主机执行命令时点停止，这一步立即结束，工具显示「已取消」；直连、SOCKS 代理、跳板机链路相同。终端标签页连接同一主机的行为不变。
- **跳板机拨号**：经跳板机连接不可达的下一跳 / 目标时点停止，这一步立即结束，不再等跳板机自身的超时。
- **本地命令（Windows）**：AI 用 `local_bash` 执行会启动常驻子进程的命令（如 `ping -t 127.0.0.1`）时点停止，这一步在秒级内结束，子进程被结束。
- **本地命令（所有平台）/ 本地 kubectl**：停止后即使仍有子进程占着输出管道，这一步也在秒级内结束。
- 不点停止时，以上所有路径的执行结果、输出与耗时不变。

## Out of scope

- 停止不终止已在远端执行的命令（SSH exec 既有行为）。
- Redis 命令、串口命令只受各自读超时约束、不跟随取消；batch 中尚未开始的子项在停止后仍会逐个尝试（各自跟随取消、快速失败）。这些都有上限，且决定 1 已保证对话恢复，本期不改。
- 复用已缓存但已失效的 SSH 连接时新建会话不跟随取消（受 SSH 保活约束）。
- 远程 SQLite（经 SFTP）读取不跟随取消。
- 后端运行器登记前点停止会丢失这次停止（这一轮照常进行，可再次停止）。
- 排队消息含 `/` 时的代码片段弹窗。
