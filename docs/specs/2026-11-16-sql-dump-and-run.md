# 转储 SQL 文件与运行 SQL 文件

> Status: Draft
> Owner: OpsKat 维护者
> Last updated: 2026-11-17（修订：导出选项）

**Objective:** 用户在数据库树上右键，就能把表、schema 或整个库转储成一个能还原的 `.sql` 文件（结构和数据 / 仅结构），也能把这样的文件在一个库上运行导入，不必再借助 Navicat 或命令行客户端。

**Hard invariant:** 没有使用这两项新功能时，现有行为不变：表数据导出（CSV / TSV / SQL / Excel）、SQL 编辑器执行、表设计器、导入向导照旧；MySQL 与 SQLite 的「查看 DDL」与表设计器里显示的建表语句一字不差；只读连接照旧拒绝写入；扩展驱动（如 Oracle）现有的功能不变，按宿主 ABI 1.0 构建的扩展照常安装、加载、工作。

## Problem

标注：**[已核实]** = 对照 opskat main（`86f40e5f`）源码或在隔离沙箱里观察确认；**[用户反馈]** = issue #368；**[用户决定]** = 本轮对话中用户选定。

1. **没有转储入口。** [用户反馈] 用户以为只能在表视图里全选后「复制为 INSERT」，希望像 Navicat 那样右键「转储 SQL 文件 → 结构和数据 / 仅结构」。[已核实] 表的右键菜单只有打开表、设计表、新建查询、新建表、清空表、删除表（`frontend/src/components/query/DatabaseTree.tsx:482-546`，沙箱截图 `e2e/scratch/issue368/01-current-table-context-menu.png`）；库节点只有新建查询、新建表、刷新。
2. **现有的 SQL 导出只有数据，且一次只能导一张表。** [已核实] 打开表后，「导出数据」选 SQL 格式可以把整张表流式导出为 INSERT 文件（`internal/app/query/export.go:157`），但文件里没有建表语句，也不能一次导出多张表或整个库。
3. **PostgreSQL 与 SQL Server 的建表语句不能用来还原。** [已核实] 这两种库的建表语句是从列信息拼出来的：PostgreSQL 缺索引、唯一约束、CHECK、外键和序列，`nextval(...)` 默认值在新库里会因为序列不存在而失败（`internal/dbdriver/postgresql/ddl.go:39-61`）；SQL Server 缺 IDENTITY、索引、约束和外键，`decimal` 丢了精度和小数位（`internal/dbdriver/mssql/ddl.go:14`）。MySQL（`SHOW CREATE TABLE`）与 SQLite（`sqlite_master` 原文）的建表语句是完整的。
4. **视图、函数、过程、触发器的定义只够「看」。** [已核实] PostgreSQL 的视图只给出 `SELECT` 正文，没有 `CREATE VIEW`；函数按名字取第一个，同名重载会丢（`internal/dbdriver/postgresql/catalog.go:139`）。MySQL 的过程与触发器写进文件时需要改分隔符，否则过程体里的分号会把语句截断。
5. **不能运行 SQL 文件。** [已核实] 应用里没有执行 `.sql` 文件的入口，转储文件只能粘贴进 SQL 编辑器。编辑器的语句切分在前端，不认 MySQL 的 `DELIMITER`，也不认 SQL Server 的 `GO`（`frontend/src/lib/sqlStatements.ts:1-4`）；内置驱动都没有声明后端切分。

## Actors and user stories

1. 作为**用 MySQL 的开发者**，我想右键一张表或几张表，导出带建表语句和数据的 `.sql` 文件，这样就能把它们搬到另一个库。
2. 作为**维护多个环境的运维**，我想把整个库（含视图、函数、过程、触发器）转储成一个文件，再在另一个库上运行它来还原。
3. 作为**用 PostgreSQL / SQL Server 的用户**，我想得到的转储文件能直接导入一个空库，不缺索引、约束、序列或自增设置。
4. 作为**导入文件的用户**，执行出错时我想知道是第几条语句、文件第几行、错误是什么，并自己决定出错时停下还是继续。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | **[用户决定]** 转储、PostgreSQL / SQL Server 建表语句补齐、整库对象（视图 / 函数 / 过程 / 触发器）、运行 SQL 文件，放在同一个变更里交付 | 用户要一次做全。Rejected: 拆成「转储框架 → 补齐 PG/MSSQL → 整库对象」三个依次交付——交付更快，但用户选了合并 |
| 2 | **[用户决定]** 入口：表节点（单选或多选）、库节点、schema 节点（有 schema 分组的库，即 PostgreSQL 与 SQL Server）都有「转储 SQL 文件 › 结构和数据… / 仅结构…」；库节点另有「运行 SQL 文件…」 | 对齐 Navicat；树上已经支持多选批量操作。Rejected: 只做表节点——整库还原是主要需求之一；schema 节点只给 PostgreSQL——前端只能按能力判断，要为此另加一项只有 PostgreSQL 声明的能力，SQL Server 用户也就少了按 schema 转储 |
| 3 | **[用户决定]** 转储对话框提供一组导出选项（见「转储 → 导出选项」）；涉及删除的「写入删除语句」默认不勾。勾上时，所有删除集中在文件开头的删除段：先拆外键，再按依赖倒序删除要转储的对象；这样覆盖还原到原来的库在每种数据库上都能成功 | 用户要求「涉及删除的都做成选项、默认不勾」，并希望像 Navicat 那样整组可选。[已核实] PostgreSQL、SQL Server 不能全局关闭外键检查，「每个对象就地先删再建」时，被外键或视图引用的表删不掉，覆盖还原会失败。交互原型：`.dev-kit/artifacts/2026-11-16-sql-dump-and-run/mockups/dump-ui.html`（本地参考）。Rejected: 不提供选项、总是写 DROP（Navicat 的转储）——默认就会删数据；只有一个删除勾选框——用户要求整组选项；勾上时每个对象就地删建——PostgreSQL、SQL Server 覆盖还原失败 |
| 4 | **[用户决定]** PostgreSQL 与 SQL Server 的建表语句补齐到能还原的程度，「查看 DDL」与表设计器随之显示补齐后的语句 | 不补齐，这两种库的转储文件无法导入。Rejected: 本轮不支持这两种库——用户要求补齐 |
| 5 | **[用户决定]** 转储出错或用户取消：立即停止，不留下文件，并说明停在哪个对象、什么错误 | 不能留下看起来完整、实际缺表的「备份」。Rejected: 保留写了一半的文件；跳过出错的表继续 |
| 6 | **[用户决定]** 运行 SQL 文件时语句失败，默认停下；可勾选「遇到错误时继续」 | 与 Navicat 一致。Rejected: 始终停下（不够灵活）；整个文件包进一个事务（MySQL 与 SQL Server 的 DDL 无法回滚，对转储文件基本无效） |
| 7 | **[用户决定]** 运行 SQL 文件与转储放在同一变更里交付 | 转储与导入闭环。Rejected: 导入另开 issue |
| 8 | 是否出现菜单项由驱动是否支持决定，不按数据库类型判断 | 项目约定共享代码不判断驱动；扩展驱动（如 Oracle）没有声明时菜单自动不出现。Rejected: 菜单显示出来、点击后再报「不支持」 |
| 9 | 转储文件、对象顺序与各数据库的写法由驱动给出 | 关外键检查、存在则删除、分隔符、批分隔符、自增插入各库写法不同。Rejected: 共享代码里按数据库拼写 |
| 10 | 导入只接受 UTF-8 文件，开头的 BOM 忽略；开始执行前先检查整个文件，有非 UTF-8 内容就拒绝执行 | OpsKat 与 Navicat 转储出来的都是 UTF-8；先检查可以避免执行到一半才发现编码错误。Rejected: 提供编码选择——没有需求；边执行边检查——会留下执行了一半的库 |
| 11 | 转储时不加锁、不开一致性快照 | 与 Navicat 默认一致。Rejected: 开快照——要求读所有表时只用一条连接，并且各数据库写法不同，留待以后 |
| 12 | 运行 SQL 文件时，确认环节就是对话框本身，不逐条预览 | 文件可能有几十万条语句。对话框写明目标库，并固定显示警告：文件会直接在该库执行，可能包含不可撤销的操作。Rejected: 沿用 SQL 编辑器「危险语句逐条确认」——对文件不现实 |
| 13 | 这两项操作都不写审计日志；结构化日志只记开始、结束、数量和耗时，不记语句与数据 | 与 GUI 里手动执行 SQL、表导入、保存表结构一致（这些都不写审计）；语句里有用户数据。Rejected: 写审计日志——与同类手动操作不一致 |
| 14 | 不包括 opsctl 与 AI 工具 | 它们是另外的入口。Rejected: 一起做——范围已经很大 |
| 15 | **[用户决定]** 资产设为只读连接时，「运行 SQL 文件…」置灰并提示原因，所有驱动一样 | [已核实] SQL Server 的连接级只读不生效，连接时只记一条日志（`internal/dbdriver/mssql/connect.go:78`），靠驱动拒绝的话，在只读的 SQL Server 资产上运行文件会真的写入。Rejected: 照常显示，由驱动在第一条写语句处拒绝——对 SQL Server 不成立 |
| 16 | **[用户决定]** 扩展驱动也能提供这两项能力：宿主 ABI 升到 1.1，本变更做宿主、SDK 与桥接层；Oracle 扩展紧接着在扩展仓库另起一轮实现 | [已核实] Oracle 扩展的建表语句用 `DBMS_METADATA.GET_DDL`，本来就完整（扩展仓库 `extensions/oracle/ddl.go:43`），也已有认 PL/SQL 块与单独一行 `/` 的切分（`extensions/oracle/split.go`）；契约现在就按 Oracle 的差异（23ai 之前没有 `DROP ... IF EXISTS`、不能全局关外键检查、PL/SQL 块以 `/` 结束、每次调用都要经 WASM）设计，以后不用为它返工 ABI。宿主现在只认 `hostABI` 1.0（`pkg/extmanifest/manifest.go:21-25`）。Rejected: 本变更不动、另开 issue——之后很可能要返工钩子；只做宿主、Oracle 不排期——Oracle 用户仍然用不上 |
| 17 | **[用户决定]** 转储文件里 INSERT 的表名不带库名；值的写法仍与「复制为 INSERT」一致 | [已核实] MySQL 的「复制为 INSERT」写成 `` `库`.`表` ``，照搬的话文件只能导回同名的库，导入别的库时数据会写回源库，不能还原。Rejected: 与「复制为 INSERT」完全一致——文件只能导回同名的库 |

## 入口

文中提到的效果图都在本地 `.dev-kit/artifacts/2026-11-16-sql-dump-and-run/mockups/`，不提交，只作参考，以本文为准。

数据库树上的右键菜单：

- **表节点**：「转储 SQL 文件 ›」放在「新建表」与「清空表」之间，自成一组，子菜单是「结构和数据…」「仅结构…」（效果图 `.dev-kit/artifacts/2026-11-16-sql-dump-and-run/mockups/04-mockup-dump-menu.png`）。多选时转储全部选中的表。选中的节点是视图时（MySQL 的表列表里有视图），只写它的定义，不写数据。
- **schema 节点**（有 schema 分组的库，即 PostgreSQL 与 SQL Server）：同一个子菜单，转储这个 schema 下的全部对象。
- **库节点**：同一个子菜单，转储这个库的全部对象；下面另有「运行 SQL 文件…」。

资产的驱动支持转储时才显示「转储 SQL 文件」；「仅结构」只要求能给出定义，「结构和数据」还要求能生成数据语句。驱动支持运行 SQL 文件时才显示「运行 SQL 文件…」。四个内置驱动（MySQL、PostgreSQL、SQLite、SQL Server）都支持两者。扩展驱动声明了相应能力时同样显示（见「扩展驱动」）；按宿主 ABI 1.0 构建的扩展照常工作，不显示这两项。资产设为只读连接时，「运行 SQL 文件…」仍然显示，但置灰，悬停提示「资产设为只读连接，不能运行 SQL 文件」；转储不受只读影响。

## 转储

**对话框。** 选择子菜单项后打开「转储 SQL 文件」对话框（效果图 `mock-dump-*.png`，布局与现有的「导出数据」对话框一致）：

- 副标题写明来源：资产名 / 库名，以及要转储的对象（选中的表名，或「整个库」「整个 schema」）。
- 「保存位置」与「选择位置」按钮：点按钮打开系统的保存对话框，默认文件名是 `<表名>.sql`（单张表）或 `<库名或 schema 名>_<YYYYMMDD>.sql`（其余情况）。目标文件已存在时由系统对话框询问是否覆盖。没有选位置之前，「开始转储」不可点。
- 导出选项（见下）。
- 选项下方一段说明，随「写入删除语句」变化：不勾时说明文件里没有删除语句，导入空库没问题，导入已有同名对象的库会在建对象处报错（运行时可勾「遇到错误时继续」）；勾上时改用警告样式，说明文件开头是删除段，导入时会删掉目标库里的同名对象和其中的数据。文件编码 UTF-8 也写在这里。

**导出选项。** 一组勾选框，分四组；转储进行中全部不可改。键盘可以用 Tab 移到每一项、用空格切换。

| 分组 | 选项 | 默认 | 不可用时 |
|---|---|---|---|
| 内容 | 导出数据（每行一条 INSERT；不勾只有结构） | 取自所选的子菜单项：「结构和数据…」勾上，「仅结构…」不勾 | 驱动不能生成数据语句时置灰、不勾 |
| 结构 | 包含索引 | 勾 | — |
| 结构 | 包含外键 | 勾 | — |
| 结构 | 包含视图 | 勾 | 只转储选中的表时置灰，提示「只转储选中的表时不包含」（选中的视图照样写定义） |
| 结构 | 包含函数 / 过程 | 勾 | 同上 |
| 结构 | 包含触发器 | 勾 | 同上 |
| 删除 | 写入删除语句（导入时先删除同名对象） | **不勾** | — |
| 导入时 | 文件开头关闭外键检查、结尾恢复 | 勾 | 驱动不能在会话里关闭外键检查（PostgreSQL、SQL Server）时置灰、不勾，提示「这个数据库不能关闭外键检查：外键会放在全部数据之后再加上」；不包含外键时也置灰 |

能关闭外键检查的库（MySQL、SQLite）在「包含外键」勾着、「关闭外键检查」不勾时，选项下方提示：表之间的外键可能让导入失败。哪些库能关闭外键检查由驱动声明，界面不按数据库名判断。

**进行中。** 点「开始转储」后显示进度条与日志：进度条上方显示「第几个对象 / 共几个 · 已写多少行」。每个对象写一行日志（结构、数据及行数）。转储进行中，对话框不能用 Esc 或点外部关闭，唯一的操作是「取消」。

**完成。** 进度条满，显示汇总：对象数、行数、文件大小、耗时；底部是「打开 ▾」（打开所在文件夹 / 打开文件，与导出对话框一致）和「关闭」。

**出错或取消。** 任何一个对象读取失败、连接断开，或用户点「取消」，都立即停止。目标位置保持开始前的样子：原来没有文件就仍然没有，原来有同名文件就仍是原来的内容。对话框用错误样式说明停在哪个对象、错误原文，并写明「未完成的文件已删除」。底部是「关闭」与「重新转储」。关闭资产标签页或退出应用，等同于取消。

**文件内容。** 依次是：

1. 注释头：OpsKat 版本、资产名、库名（及 schema）、所选的导出选项、生成时间。不写主机地址、端口和账号。
2. 驱动给出的文件开头，例如 MySQL 的 `SET NAMES utf8mb4`；勾了「关闭外键检查」时，再加 MySQL 的 `SET FOREIGN_KEY_CHECKS = 0`、SQLite 的 `PRAGMA foreign_keys = false`。
3. 删除段（只在勾了「写入删除语句」时）：不能关闭外键检查的库先删除要转储的表上的外键；再按依赖倒序删除触发器、函数与过程、视图、表，最后删除类型。每条都是「存在则删除」的写法，不带 CASCADE。
4. 整库或整个 schema 转储时，PostgreSQL 写列用到的枚举类型；只转储选中表时，只写这些表的列用到的枚举类型。
5. 每张表依次是：注释分隔行、建表语句（含主键、唯一约束、CHECK、注释；勾了「包含索引」时含索引，依库而定在建表语句里或紧随其后）；勾了「导出数据」时，接着写全部行，每行一条 INSERT。值的写法与「复制为 INSERT」对同一行生成的一样，但不含生成列 / 计算列，表名也不带库名（MySQL 的「复制为 INSERT」会带上库名，带着的话文件导入别的库时，数据会写回源库）；「复制为 INSERT」本身不变。
6. 外键（勾了「包含外键」时）：不能关闭外键检查的库（PostgreSQL、SQL Server），在全部表与数据之后用「修改表、加外键」写出；能关闭的库（MySQL、SQLite），留在建表语句里。不勾时文件里没有外键。
7. 视图（勾了「包含视图」时）：按依赖顺序写出，被依赖的视图在前。
8. 函数与过程（勾了「包含函数 / 过程」时）。
9. 触发器（勾了「包含触发器」时）：在所有数据之后写出，避免导入数据时被触发（SQLite 的触发器也在此）。
10. 序列与自增的收尾：PostgreSQL 的序列在数据之后同步到当前值。
11. 驱动给出的文件结尾，例如恢复外键检查。

只转储选中的表时没有第 8、9 部分；选中的视图按第 7 部分写。不勾「写入删除语句」时，文件里没有任何删除语句。

**各数据库的完整度要求**（以下按全部结构选项都勾着说明；「能还原」指：把文件在一个空库上运行后，表、列类型、默认值、约束、索引、外键、自增 / 序列当前值、视图、函数、过程、触发器与原库一致，行数相同；勾了「写入删除语句」时，把文件运行回原来的库也得到同样的结果）：

- **MySQL**：建表语句用服务器给出的原文（不勾「包含索引」「包含外键」时，从原文里去掉对应的行）；视图、过程、函数、触发器也用原文（含 `DEFINER`，与 Navicat 一致）。过程、函数、触发器用 `DELIMITER ;;` 包起来。
- **PostgreSQL**：建表语句补齐列类型（含长度、精度）、默认值、非空、主键、唯一约束、CHECK、`GENERATED ... AS IDENTITY`；属于该表列的序列先建出；索引（不含由约束自动建出的）单独写出；表与列注释用 `COMMENT ON` 写出。视图写成完整的 `CREATE VIEW`；同名重载的函数每个都写出。只写枚举类型；domain、复合类型、range 类型与扩展（`CREATE EXTENSION`）不写，用到它们的表在导入时会报错（见 Out of scope）。`GENERATED ALWAYS` 身份列的数据用 `OVERRIDING SYSTEM VALUE` 插入。
- **SQL Server**：建表语句补齐类型的长度、精度与小数位、`IDENTITY(种子, 增量)`、默认值、主键、唯一约束、CHECK；索引单独写出。有 IDENTITY 列的表，插数据时用 `IDENTITY_INSERT` 开、关包起来。每个批次后写 `GO`。视图、函数、过程、触发器用服务器保存的原文（勾了「写入删除语句」时，删除段里对它们写「存在则删除」）。列注释（扩展属性）不写。
- **SQLite**：表、索引、视图、触发器都用 `sqlite_master` 里的原文。

PostgreSQL 与 SQL Server 补齐后的建表语句，也就是「查看 DDL」与表设计器里显示的语句。

**规模。** 表的数据边读边写，不整表留在内存里，几百万行的表也一样。

## 运行 SQL 文件

**对话框。** 在库节点选「运行 SQL 文件…」打开（效果图 `mock-run-*.png`）：

- 副标题：在 资产名 / 库名 上逐条执行文件里的语句。
- 「SQL 文件」与「选择文件」按钮（系统打开对话框，筛选 `*.sql`，也允许所有文件）。选好后显示文件大小。
- 「遇到错误时继续」勾选框，默认不勾，说明文字：不勾时在第一条失败的语句处停下；已执行的语句不会回滚。
- 固定的警告：文件里的语句会直接在 **库名** 上执行，可能包含 `DROP TABLE`、`DELETE` 等不可撤销的操作。
- 没有选文件之前，「开始运行」不可点。

**开始之前。** 先检查整个文件。有非 UTF-8 的内容就不执行任何语句，提示「文件不是 UTF-8 编码」并给出第一处出现的行号。文件开头的 BOM 忽略。

**执行。** 所有语句按文件顺序、在这个库上同一条连接里执行，所以文件里前面设置的会话状态（如关闭外键检查）对后面的语句有效。每条语句单独提交，不包事务。切分由驱动按自己的写法完成，至少要认得：引号与转义、单行和多行注释、MySQL 的 `DELIMITER`、PostgreSQL 的 `$$` / `$tag$` 块、SQL Server 的 `GO` 批分隔符（一个批次作为一次执行）、SQLite 触发器的 `BEGIN ... END`。本功能转储出来的文件，以及 Navicat 与 mysqldump 的 SQL 文件，都要能正确切分。文件边读边执行，不整个读进内存。

**进行中。** 进度条显示「已执行多少条 · 已读多少 / 共多少 MB」，日志每一万条写一行。底部是「停止」：当前语句执行完后停下，结果按「已停止」显示。进行中对话框不能用 Esc 或点外部关闭。

**语句失败。**

- 没勾「遇到错误时继续」：停下。用错误样式显示第几条语句、在文件第几行开始、数据库返回的错误原文、语句开头一段（截到约 200 个字符），并写明之前执行的语句不会回滚。底部只有「关闭」。
- 勾了：记下失败，继续下一条。日志里写出每条失败的条号、行号和错误；超过 100 条失败后，日志只再写一行「后续失败不再逐条列出」，但继续计数。结束时显示成功与失败各多少条。

**遇到不支持的写法时停下**（勾了「继续」也照样停下）：PostgreSQL 的 `COPY ... FROM stdin` 与 psql 的反斜杠元命令。提示写明是什么写法、在哪一行，并说明这类文件请改用对应的命令行工具导入。

**完成后。** 显示汇总（成功条数、失败条数、耗时），并刷新这个库在树上的表与对象列表。关闭资产标签页或退出应用，等同于点「停止」。

## 扩展驱动

- 宿主 ABI 升到 1.1：宿主同时加载按 1.0 和 1.1 构建的扩展。1.0 的扩展行为不变，它们的驱动不显示转储与运行 SQL 文件。
- 按 1.1 构建的扩展驱动可以声明这两项能力。按 1.0 构建却声明了它们的扩展，加载时报错，错误里点名扩展与能力。
- 扩展驱动的转储与运行 SQL 文件，对用户的表现和内置驱动完全一样：同样的入口、对话框、进度、取消与出错规则、目标文件保持原状、UTF-8 预检、停下与继续、不支持写法的提示。读写文件、排序、进度与取消由宿主完成，扩展只提供各自数据库的写法与切分。
- 运行 SQL 文件时，扩展驱动的语句同样在这个库上同一条连接里按顺序执行，前面的会话设置对后面的语句有效。宿主把语句分批交给扩展，不是每条语句调用一次。
- 扩展 SDK 提供实现这两项能力需要的接口与说明，扩展作者不需要读宿主源码。

## 隐私与日志

- 转储文件的注释头不含主机、端口与账号；文件里的数据就是表里的数据。
- 应用日志只记操作开始与结束、资产 ID、库名、对象数、行数或条数、失败数和耗时，不记语句与数据。
- 这两项操作都不写审计日志（决定 13）。

## Out of scope

- Oracle 扩展本身的实现（还原所需的写法、对 19c 等真实库的往返测试、0.3.0 发布）：紧接本变更，在扩展仓库另起一轮，有自己的 spec 与 PR。本变更只提供宿主 ABI 1.1、SDK 与桥接层，并用仓库内的扩展测试夹具验证。
- opsctl 与 AI 工具的转储 / 导入入口。
- 转储时的一致性快照与锁表（决定 11）：转储期间有写入，表与表之间可能不一致。
- PostgreSQL 的 domain、复合类型、range 类型、扩展、权限（`GRANT`）、所有者；SQL Server 的扩展属性、权限、架构（schema）的创建；MySQL 的事件（event）与用户权限。
- 导入 pg_dump 的 COPY 格式与 psql 元命令（遇到时提示并停止）；导入非 UTF-8 文件。
- 转储为压缩文件、按表拆成多个文件、多行合并的 INSERT。
- Navicat 的「复制表」（在库内复制一张表）。
