# Architecture

The canonical map of how OpsKat is put together: the processes it runs, the backend layering, the request lifecycle, each subsystem, the data model, and the AI / extension / opsctl flows.

> This doc owns **structure** (what the pieces are and how they fit). It does *not* repeat the cross-cutting **principles** (SOLID seams, Fix policy, Reuse first, defensive code) — those live in [AGENTS.md](../AGENTS.md) — nor the **how-to** (commands, conventions, logging rules, generated files) — those live in [DEVELOP.md](DEVELOP.md). The step-by-step path for adding a built-in asset type is in [adding-an-asset-type.md](references/adding-an-asset-type.md).
>
> **Keep it true for the current branch.** Every claim here must be verifiable in committed code. Counts (asset types, migrations, stores) are deliberately written as "enumerate from `<source>`" rather than hardcoded — they drift silently. Before editing, read [DOC-MAINTENANCE.md](DOC-MAINTENANCE.md).

## 1. Topology — desktop app and opsctl, no app HTTP API

OpsKat is a **Wails v2** desktop app (Go 1.26 backend + React 19 frontend). The frontend and backend communicate over **Wails IPC only** — there is no REST/HTTP server for the app's own UI. `opsctl` talks to the running app over two **local IPC endpoints** (Windows named pipes; Unix-domain sockets on macOS/Linux), and extensions run as sandboxed **WASM** modules inside the backend (and inside `opsctl` itself when it executes on an extension asset — see [§7](#7-extensions--wasm-plugins)).

```
┌──────────────────────────────────────────────────────────────────┐
│  Desktop app (single process)                                      │
│                                                                    │
│   React 19 frontend  ──Wails IPC──►  internal/app (bindings)       │
│   (frontend/)                            │                         │
│        ▲  EventsOn/Emit                  ▼                         │
│        │                            internal/service               │
│        │                                 │                         │
│        │                            internal/repository            │
│        │                                 │                         │
│        │                            GORM ─► SQLite (opskat.db)      │
│        │                                                            │
│        │   WASM (wazero)  ◄── pkg/extension ── internal/ai (tools)  │
│        │                                                            │
│   sshpool / connpool  (live SSH conns + protocol tunnels/proxies)  │
└───────┬────────────────────────────────────────────────────────────┘
        │ approval.sock
        │ (approve / grant)
        ▼
   opsctl CLI  ── headless asset ops (exec / create / update / delete / cp / batch) ──►
   (cmd/opsctl, also embeddable in the app via internal/embedded)
```

- **Desktop app** — the Wails process. Owns the DB, credential keys, connection pools, the AI runner, and the WASM extension runtime.
- **`opsctl` CLI** — a standalone binary (`cmd/opsctl`) for headless/scripted asset operations. It dials its own connections, so a running command outlives the desktop app; it asks the app for approval over local IPC only when it cannot prompt in the terminal itself. Can be embedded in the app (`internal/embedded`, build tag `embed_opsctl`) and installed to the user's PATH.
- **Extensions** — WASM modules loaded by `pkg/extension` (wazero runtime). The host exposes a narrow permission surface; the AI calls extension tools through a single dispatcher. There is no separate extension host: developing one means installing it into a running app with `opsctl ext dev` ([§7](#7-extensions--wasm-plugins)).

## 2. Backend layering

Bindings stay thin: parse → delegate → return. Business rules live in `service/`, persistence in `repository/`. **Logic placed directly in an `App` binding is unreachable from tests and from `opsctl`** — so it doesn't belong there.

```
main.go
  └─ internal/app/        IPC boundary (Wails-bound structs, "binders")  ── validate here
       └─ internal/service/        *_svc — business logic, validation, orchestration
            └─ internal/repository/    interface + impl + mock — data access
                 └─ internal/model/entity/   GORM entities
```

**Dependency rule (DIP).** A layer depends on the **interface getter** of the layer below, never on a concrete struct. Services call `asset_repo.Asset()` (the `AssetRepo` interface), repositories reach GORM through cago's `db.Ctx(ctx)`. Implementations are swapped behind the interface in tests via the generated `mock_*/` packages. A service must not import another service's repository or call back into `App`; `internal/app/*` must not touch repositories or the DB directly.

**Registration, not branching (OCP).** Repositories and services are wired as global singletons at startup: `RegisterXxx(NewXxx())` installs the implementation, `Xxx()` returns it. New protocol behavior plugs in by *registering* (an asset-type handler, an AI tool, a policy) — not by adding a `switch assetType` to shared code. See [AGENTS.md → SOLID](../AGENTS.md#high-cohesion-low-coupling--solid) for the seams this enforces.

**SQL databases are a registry too.** The `database` asset type has no per-engine code in shared layers: the driver contract — `Driver`, the serializable `Descriptor`, `Session`, the request and result types, and the driver's view of the asset config (`Config`) — is the public package `pkg/dbdriver`, with the shared `database/sql` session implementation in `pkg/dbdriver/sqldb`; neither imports any `internal/` package and both build for `GOOS=wasip1`, so an extension can implement the same contract (guarded by `TestPublicDriverContractStandsAlone` in `internal/archtest`). `internal/dbdriver` is the host's registry of drivers (`Register` / `Lookup` / `ByName` / `List`, and `TryRegister` / `Unregister` for the drivers an extension provides), the built-ins MySQL, PostgreSQL, SQL Server and SQLite are its sub-packages linked by `internal/dbdriver/builtin`, and each driver supplies its `Descriptor` (id, display name, icon, aliases, default port, form fields per tab, capabilities), the asset-config rules, and a `Session` it opens and owns. Drivers never see the stored `asset_entity.DatabaseConfig`: the entity converts it to and from `dbdriver.Config` (`DriverConfig` / `SetDriverConfig`; password, credential and proxies stay host-side). Connection (`connpool.OpenDatabase`, which resolves tunnels / proxy chains and hands the driver a `Transport`), the query panel's SQL execution, tree and table browsing, export reads, table DDL, test connection and AI / opsctl SQL execution all go through that session and exchange structured results; shared code does not build dialect SQL for the read path. An asset whose driver is not registered fails with `dbregistry.ErrDriverUnavailable` (the registry's error) naming the driver. The write path (grid edit, create / alter / drop / truncate, create database, import, export / copy as SQL) is generated the same way: the session's write methods (`GridEditStatements`, `CreateTableStatements`, `AlterTableStatements`, `ImportStatements`, `PrepareRowStatements`, …) return the statements, and the query panel previews and executes exactly those. A batch of schema statements (`Query.ExecuteSchemaStatements` → `query_svc.RunSchemaBatch`) runs on the session's `ExecuteBatch` in one transaction, all or nothing, when the descriptor declares `TransactionalDDL`, and otherwise one by one, stopping at the first failure; the result reports each statement as executed / failed (with the database error) / not executed, and whether the batch was rolled back. See [Adding a database driver](references/adding-a-database-driver.md).

**Underlying framework.** The backend is built on the **cago** framework (`github.com/cago-frame/cago`): DB registration/access (`db.Database()` / `db.Ctx(ctx)`), the structured logger (`pkg/logger`), and config sources. The AI agent loop comes from the sibling **cago-agents** module (`github.com/cago-frame/agents`): `app/coding`, `agent`, `tool`, `provider/*` (see [§6](#6-ai-subsystem)).

## 3. Request lifecycle

A representative read, traced front to back:

1. **Frontend** calls a generated Wails binding, e.g. `System.GetAsset(id)` from `frontend/wailsjs/go/system/System` (the `wailsjs/` bindings are **generated & gitignored** — the producer is the Go side in `internal/app/*.go`).
2. **Binding** (`internal/app/system/asset.go`) — a thin method on the bound `System` struct. It wraps the Wails context with the current language (`i18n.Ctx(s.ctx, s.Lang())`) and delegates: `asset_svc.Asset().Get(ctx, id)`. Boundary inputs are validated here / in the service; this is one of the **validate-at-the-boundary** points (alongside WASM host calls — see [AGENTS.md → Defensive Code](../AGENTS.md#defensive-code--error-handling-no-meaningless-fallbacks)).
3. **Service** (`internal/service/asset_svc`) — runs business logic (validation, defaults, e.g. seeding the default command policy on create), then calls the repository interface getter `asset_repo.Asset()`.
4. **Repository** (`internal/repository/asset_repo`) — issues the GORM query through `db.Ctx(ctx)`, filtering on `status = StatusActive` (soft delete, [§5](#5-data--persistence)).
5. **Return** — entity → service → binding → Wails marshals JSON → frontend store updates → subscribed components re-render.

Backend-initiated updates flow the other way as **events**: the app emits a Wails event (e.g. `data:changed`) and the frontend re-fetches via `EventsOn` (see [§8](#8-frontend)).

## 4. Process wiring (`main.go`)

`main.go` is the composition root. In order, it: resolves the data dir / master key (`OPSKAT_DATA_DIR` / `OPSKAT_MASTER_KEY` override; otherwise `bootstrap.AppDataDir()` returns the **portable** dir — `data/` next to the executable, see `internal/pkg/portable` — and falls back to the per-platform dir); runs `bootstrap.Init` (master-key resolve, DB open, repository registration, migrations); initializes the logger and config; builds the shared infrastructure (SSH pool, SFTP service); constructs the per-domain **binders** and hands them to `wails.Run` via `Bind`.

**Outbound (non-asset) HTTP.** Requests the app makes for itself rather than for an asset — update check and download (`update_svc`), the extension store index (`extstore_svc`) and package pulls (`ociclient`), GitHub backup (device-flow login, gists) and WebDAV backup (`backup_svc`) — all send through `netproxy.Transport()`, the single process-wide `http.RoundTripper`. It always reads the settings last passed to `netproxy.Set`, so changing the network proxy applies without restart: `custom` sends everything except the bypass list through the configured proxy, `direct` never uses one, `env` follows the proxy environment variables. It is a clone of `http.DefaultTransport` (which itself is never modified) dialing through `internal/pkg/netdial`; each client keeps its own timeout and redirect policy. Asset connections do not use it (they have their own tunnels and proxy chains).

**Portable mode** shapes three more decisions, all of which must keep the host machine untouched and let the folder travel. `bootstrap.Init` keeps the master key in `<dataDir>/master.key` instead of the OS keychain — keyed off the *resolved* data dir, so an explicit `--data-dir` / `OPSKAT_DATA_DIR` pointing at an installed dir still uses the keychain. The two below instead key off `internal/pkg/portable` alone, which an override does not move. `main.go` then points WebView2's user-data dir at `<portable>/webview2` (Wails otherwise defaults it to `%APPDATA%\opskat.exe`, which would strand the frontend's `localStorage` — open tabs, editor buffers — on the host), and salts the `SingleInstanceLock` id with the portable path so a portable build started next to an installed one gets its own window instead of silently handing off and exiting. `OPSKAT_E2E` relaxes the single-instance lock for the e2e harness.

Binders implement a small `Lifecycle` (`Startup(ctx)` / `Cleanup()`) that `main.go` drives explicitly from Wails' `OnStartup` / `OnShutdown` hooks (Wails does not auto-call lifecycle methods on bound structs). The extension subsystem is initialized **asynchronously after startup** so WASM compilation never blocks the UI coming up.

## 5. Data & persistence

- **Store:** GORM over **SQLite** (`opskat.db` in the data dir), opened during `bootstrap.Init` and registered as the cago `db` singleton.
- **Migrations:** `gormigrate` (`go-gormigrate/gormigrate/v2`), one append-only list in `migrations/migrations.go`, run from bootstrap. New migrations are **appended**; old files never change. Enumerate them from `git ls-files 'migrations/*.go'` — don't hardcode a count.
- **Soft delete:** via a `Status` field, **not** GORM's `DeletedAt`. `StatusActive = 1` / `StatusDeleted = 2` are defined in `internal/model/entity/asset_entity/asset.go`; queries filter `status = StatusActive`. (Distinct from `internal/status/`, which is unrelated system-health reporting.)
- **Entities:** one package per domain under `internal/model/entity/` — enumerate with `git ls-tree --name-only -d HEAD internal/model/entity/` (asset, credential, group, policy_group, conversation, audit, grant, host_key, forward, ai_provider, snippet, ssh_agent_source, extension_state, extension_data, extension_describe, and the shared `policy` package).
- **Credential encryption:** done in `internal/service/credential_svc` — **Argon2id** to derive a key from the master key + a per-install KDF salt, then **AES-256-GCM** for each secret. The **master key** is resolved by `credential_svc.ResolveMasterKey` (priority: explicit arg/env → OS keychain via `zalando/go-keyring` → `<dataDir>/master.key` file → freshly generated). `internal/bootstrap` only *resolves and injects* the key + salt (the KDF salt is persisted base64 in `config.json`); the crypto itself lives in `credential_svc`.

> "Command policy" is three different things — don't conflate them: (1) the shell-rule matching engine in `internal/ai/policy/command_rule.go` + `command_shell.go` (there is **no** `command_policy.go` source file); (2) the `command_policy` JSON column on the assets table (`asset_entity.Asset.CmdPolicy`); (3) `asset_entity.DefaultCommandPolicy`, a re-export of `policy.DefaultCommandPolicy` from `internal/model/entity/policy`.

## 6. AI subsystem

`internal/ai/` turns a conversation into guarded tool calls against assets. Its subpackages (enumerate with `git ls-tree --name-only -d HEAD internal/ai/`):

| Package | Responsibility |
| --- | --- |
| `runner` | Builds the cago-agents `coding.System` + `agent.Runner` (provider, tools, middleware) and drives Send/Cancel/Steer. Registers an **audit middleware** around every tool call and an optional gate for local file/shell tools. |
| `tool` | The tool registry. `Tools()` exposes the asset / group / exec / extension / transfer tools to the AI as `agents/tool.Tool`s. The unified `exec` / `help` pair is the only AI command path for any asset type with a registered executor — built-in **or** extension-provided; `AllToolDefs()` is the name→handler table shared with opsctl, while opsctl keeps its own batch command. The tool list is therefore independent of how many extensions are installed. |
| `policy` | Per-protocol rule checkers — `query_policy.go` (SQL, parsed with the TiDB parser), `redis_policy.go`, `mongo_policy.go`, `k8s_policy.go`, `kafka_policy.go`, plus shell-command rules in `command_rule.go` / `command_shell.go` (shell AST via `mvdan.cc/sh`). |
| `permission` | Dispatches an asset type to its policy checker, merges asset + group-chain effective policy, and returns Allow / Deny / NeedConfirm. Owns the grant flow (matching previously-approved DB grants, submitting new ones for approval). File transfer authorizes **each endpoint separately, under that endpoint's own asset type**. For an SSH endpoint, the registered `cp:read` / `cp:write` faces keep the transfer direction while the subject remains the **remote path**: command-policy allow rules may explicitly grant `cp:read:<path-rule>`, `cp:write:<path-rule>`, or both via `cp:*`; otherwise the checker falls through to the existing `cp` grants, whose path matching uses `policy.MatchPathRule`. These `cp:` rules are removed from shell-command matching, so a path rule cannot authorize an executable command. For an object-storage endpoint it is the `oss` face instead: the subject is a policy string such as `object.read <bucket>/<key>`, and it goes through the OSS policy and OSS grants — path-shaped rules are never matched against a bucket/key, and the reverse. A local endpoint produces no approval item. Grant matching isolates the `cp` surface from all non-`cp` command surfaces so a path grant can never authorize a command, or the reverse; strict per-type isolation among non-`cp` grants is deferred because existing rows were stored as `tool_name="exec"`. |
| `helper` | Protocol clients (SSH, SQL, Redis, Mongo, Kafka, etcd, Serial, K8s). **No entry point here checks permissions.** The `Exec*OnAsset` functions are pure execution bodies; the check happens in `tool.handleExec` before dispatch. Calling one from a new site without a `permission` check bypasses policy. Enumerate them with `git grep -n "^func Exec.*OnAsset" -- internal/ai/helper/`. Object storage has both: `ExecOSSOnAsset` is the AI/opsctl command body, while the desktop bucket browser stays an app surface. (RDP and VNC are interactive app surfaces only, with no helper here.) |
| `audit` | Writes a tool-call audit log after execution, with per-tool command-summary extractors. Also the entry point for the desktop binder's asset create/update/delete rows (`WriteAssetChange`), so all three `audit_logs.source` values (`ai` / `opsctl` / `desktop`) share one set of column semantics. |
| `aictx` | Shared context keys and the decision primitives (Allow / Deny / NeedConfirm, the `CheckResult` slot) used across the packages above. |
| `assetref` | Resolves the `asset` tool argument (numeric id **or** name) to an `*asset_entity.Asset`; a name matching more than one asset is an error rather than a silent first-match. Used by `exec` / `help` / `batch_exec` and by the audit middleware. |
| `skills` | Embeds one `<asset-type>/SKILL.md` per registered type documenting its `put_asset.config` contract and, when available, `exec` syntax (cago skill format: frontmatter + body). `help` serves the body to both AI and opsctl; a consistency test compares the documented config-field table with the handler-owned automation declaration. |
| `cmdline` | Quote-aware command-line tokenizing + flag parsing shared by the per-type `exec` DSLs (mongo / etcd / kafka) and k8s kubectl args. Lexical only — verb/flag legality belongs to each type's `<name>_command.go`. |
| `execimpl` | Registers `helper` execution bodies and per-type help documents with `permission`. Giving a new asset type command support means adding its `SKILL.md` and registering its executor plus any canonicalizer or precheck here; types without a command surface register help only. |

**Tool-call flow:** the LLM emits a tool use → cago's loop runs the middleware chain → the handler asks `permission` to check the asset's policy → **Allow** runs it; **Deny** returns a refusal to the model; **NeedConfirm** prompts the user (and, on "allow all", persists a **grant** so future matching calls skip the prompt) → the result and the recorded decision (source + matched pattern) are written to the audit log. Extension tool calls take the same path: the extension's asset types register an executor and a `PolicyCheckFunc` (see [§7](#7-extensions--wasm-plugins)), so a call is canonicalized, policy-checked, prompted, granted and audited exactly like a built-in one — only the middle judgement differs, asking the guest's `check_policy` to classify the call into an action plus the resources it touches (or, for a tool declaring the SDK's `RejectArgs`, to refuse arguments that can never run — denied before any rule or grant, never prompted, audited as a deny), and judging each resource against the `ext:` policy groups and own rules the asset carries (`internal/ai/policy.CheckExtensionPolicy`: any resource hitting a deny refuses, every resource must be covered by an allow rule or a session grant to run unattended — `permission.MatchExtensionGrant` covers per resource; resources are `path.Match` globs, a wildcard resource being denied when a deny glob may match one of its names and allowed only when an allow glob covers all of them). A multi-resource decision's audit `matched_pattern` lists every rule/grant that allowed it, or each deny rule with the resources it denied. Transfers go through a single `cp(src, dst, recursive)` tool: each endpoint is either a local path or `<asset>:/<path>`, and every asset endpoint runs the same gate under its own type's face before any byte moves, so a transfer is prompted and audited exactly like a command. Recursive and glob transfers approve the source and destination directory/object-prefix scopes before listing; only after those scopes are allowed does the shared tool enumerate and transfer their contents. `opsctl cp` submits the same scopes over `approval.sock` and delegates enumeration to the tool, so approval never requires a preliminary recursive scan. During one `cp` command, all list/read/write operations for the same SSH asset share one task-scoped SFTP session; AI calls build that session on the existing per-send SSH cache, while opsctl owns and closes the equivalent task cache around the whole command. The bytes themselves always move through `internal/pkg/sftpio` — as do the desktop file manager's transfers — because it is the only path that issues SFTP requests concurrently; `io.Copy` / `File.Write` degrade to one 32KB packet per round trip, and its concurrent writes oblige every caller to delete the partial destination on failure.

**The unified `exec` tool's ordering is load-bearing** (`tool/tool_handlers_unified.go`): resolve the asset and optional type assertion → validate a non-empty command → look up its executor → enforce the per-conversation **doc gate** → canonicalize when the type registered a `CanonicalizeFunc` → run any per-type `PrecheckFunc` → **then** perform the permission check and execute. Every side-effect-free judgement must run before `CheckForAsset`, because `NeedConfirm` blocks on a user-visible approval dialog whose "allow all" may persist a grant. Policy matching, the approval dialog, and audit use the canonicalized command; execution receives the raw command. Pre-permission failures record a deny decision with an `exec_*` source so audit can distinguish them from execution. The permission lookup itself is fail-closed: ordinary callers require an injected checker, while opsctl may omit it only on a context explicitly marked as already approved.

For the exact logging obligations on this path, see [DEVELOP.md → Logging for key flows](DEVELOP.md#logging-for-key-flows).

## 7. Extensions — WASM plugins

The extension stack is three layers, and the dependency points one way. **`pkg/extmanifest`** is the pure-data security contract: `manifest.json`, the permissions it grants, and the rule that decides whether this app can run it (`HostABIVersion`, `SupportedHostABIs`, `CheckCompatible`). The store index (`pkg/extstore`) and the publisher in the extensions repo depend on it alone — no WASM runtime. **`pkg/extension`** is the runtime: wazero, the instance pool, the host functions, permission enforcement and the contribution-point registry. It knows nothing about asset types, tools, policies, snippets, database drivers or pages — `TestExtensionRuntimeStaysContributionAgnostic` in `internal/archtest` keeps it from importing `pkg/dbdriver`, `pkg/extwire` or any `internal/` business package. **Contributions** are defined, validated and attached by the subsystem that owns them: `internal/extreg` (asset types, tools, policy, pages, database drivers), `internal/service/snippet_svc` (snippets).

**The runtime.** The WASM module is a WASI **reactor** (`GOOS=wasip1 go build -buildmode=c-shared`) exporting `opskat_call` plus `malloc` / `free`, and importing exactly two host functions — `host_call` (JSON control plane) and `host_io` (binary data plane). Key files: `runtime.go` (compile, instance pool, `Plugin.CallTool` / `Plugin.CancelTool` / `Plugin.Describe`), `lease.go` (`Plugin.Lease`: an instance bound to a `Scope` for callers that hold one across calls), `invocation.go` (per-call IO handle table + cancellation), `scope.go` (the call scope), `host_capability.go` (permission enforcement), `host.go` / `host_module.go` / `hostfn.go` / `host_default.go` (the host function surface), `contribution.go` (the contribution points), `descriptor.go` + `describe.go` (the `describe()` answer and its cache seam), `manifest.go` (the runtime's manifest: the contract plus `describe()`'s presentation and raw contributions), `bridge.go` (the name → loaded-extension lifecycle table), `manager.go` (scan / load the extensions dir).

**What an extension declares, and where.** `manifest.json` carries only the **security contract** — `name` / `version` / `minAppVersion` / `hostABI` / `backend` / `permissions` / `contributes.databaseDrivers` — because that is what a user must be able to audit *before* the code runs. It is parsed strictly. Everything else is answered by the module itself through **`describe()`**: `icon`, `i18n` and `contributes`, whose keys are `assetTypes`, `tools`, `policy`, `snippets`, `pages` and `databaseDrivers` (`extwire.Key*`). The wire format is one shared package, `pkg/extwire`, used by both the guest SDK and the host. The guest SDK (`pkg/extsdk`, package `opskat`) derives the answer from the registration calls — `opskat.Tool("list_objects", handler).Policy("read").Doc(...)` fixes the tool's name, policy action, documentation and (by reflecting the handler's own argument type) its parameter schema in one place — so the declaration cannot drift from the code that serves it. See [extensions/README.md](../extensions/README.md) for the author's side.

**Contribution points.** Each `contributes` key belongs to one `extension.ContributionPoint` (`Key` / `Check` / `Attach`). `Check` sees the whole extension through a read-only `extension.ExtensionView` (permissions and every contribution) so cross-contribution rules live in the point that owns them; `Attach` wires the contribution into its subsystem and returns a revoke function. A process builds one `extension.ContributionRegistry` from `extreg.Points()` before loading any extension — the desktop app (`main.go`) and opsctl (`cmd/opsctl/command/ext.go`) register the same set — and `Manager` runs it on every load: all points `Check`, then all `Attach` in order, and one failure revokes what was attached and the extension does not load. An undeclared key, a key no point is registered for, and a bad entry all fail the load with an error naming the extension, the contribution and the entry. Uninstall and disable revoke every contribution. Tool and policy rules that moved out of the runtime live in `internal/extreg` (`tools.go`, `policy.go`); an asset type's `configSchema` rules in `assettypes.go`; page slot and bundle-path rules in `pages.go` (`extreg.PageSlots`, an independent copy of `frontend/src/extension/slots.ts`, compared by `TestPageSlotsMatchFrontend`); snippet rules, with the built-in category list owned by the snippet category registry, in `snippet_svc/extcontrib.go`; driver descriptors and the manifest/`describe()` id match in `dbdrivers.go`.

**`extreg.Manifest`: the structured view.** The runtime's `extension.Manifest` keeps `describe()`'s contributions raw (`Contribution(key)` / `ContributionKeys()`). `extreg.ManifestOf` decodes them into the typed `extreg.Manifest` (asset types, tools, policies, pages, snippets, database drivers) that the rest of the app — help documents, tool-argument validation, the frontend's extension list — reads; `(*Manifest).Localized` resolves its i18n keys.

**Tools are the one callable unit.** A tool is either a **policy tool** (declares a policy action; reached by AI `exec` and opsctl through the asset, and by the extension's pages) or **page-only** (`pageOnly`; pages only, absent from `help`, refused by `exec`). `policy.type` and an asset type are required only when some tool declares a policy action. Any tool can emit events and be cancelled; a page-only tool may declare `noTimeout`; a string parameter can be marked `large` so opsctl fills it from `--<name>-file`. There is no separate "action" call.

**The asset a call runs against is injected, not declared.** `exec <asset> -- <tool>` already names the asset, so it travels in the call envelope (`extension.ToolCall.Asset`, an `extension.AssetRef`) and the guest reads it off `ToolContext.Asset`; `ctx.AssetConfig()` is the `asset.get_config` host call applied to it — the op takes no id (a guest-supplied `asset_id` is refused), and the host serves the config only if the asset's type is registered by the calling extension, deciding plaintext vs. credential handle by the extension's own `permissions.credentials`. A tool **may not declare an `asset_id` parameter** — `pkg/extsdk` panics at registration and the tools point refuses the `describe()` answer — because policy, approval and grant are all keyed on the exec target, and a second asset id in the arguments would reach an asset the user never granted. A page's call (`CallExtensionTool` / `CancelExtensionTool` in `internal/app/extension`) carries the asset id the page was opened on; `0` means no asset. It is the user's own action in the page, so it runs directly through `Plugin.CallTool` with no policy check, approval, grant or audit (AI `exec` and opsctl on the same asset stay fully gated), but it is still scoped to its asset, its arguments are checked against the tool's declared schema (`extreg.ValidateToolArgs` — unknown keys and opsctl's `-file` spelling are rejected), and it honors cancellation and the tool's timeout (`extreg.ToolTimeout`). Calls and their events are addressed by invocation id: the frontend mints it in `frontend/src/extension/api.ts` (it needs it before the call returns) and the binder refuses an empty one or one shaped like the runtime's own `<ext>#<n>` ids (`extension.IsRuntimeInvocationID`), so a page can only name its own calls; `Plugin.CancelTool` / `CancelExtensionTool` stop that one run, and every `ext:tool:event` carries the extension and id, so one extension's concurrent calls are tracked and cancelled separately. Events go to the page only; AI `exec` and opsctl drop them.

**Scope-based gating.** Every call runs in an `extension.Scope`, resolved by the subsystem that owns the call's asset, and `capHost` (`host_capability.go`) admits each stream and ticket request against that scope and the manifest's permissions — it never reads an asset type's declaration. A scope carries the asset, its `Endpoints`, a `Route` (the connection path: SSH tunnel / proxy chain dialer, and whether it is direct), TLS settings, credential injection (`RequestAuth`), a `TicketSource` and optionally `Ops`, the closed list of host calls a call may make. Admission order: a `permissions.network.http` target is dialed directly (private destinations only with `network.allowPrivate`); an endpoint of the scope is reachable with `network.assetEndpoint`, along the route with the asset's TLS and injected credentials; any other address only with `network.assetRoute` and a scope that has a route (a direct route resolves the target here, refuses a loopback, link-local, unspecified or own-interface address other than the asset's own, and dials the address it checked); everything else is refused with a log line naming extension, asset and target. `auth.kerberos_ticket` answers only from a scope with a ticket source and with `permissions.kerberos`. A call with no asset has an empty scope. Two resolvers exist: for an extension asset type, `extreg.AssetScope` builds it from the type's declaration (`extension_svc.Service.ResolveScope`, installed as `DefaultHostConfig.Scopes` by `Service.HostConfig`; the connection path is built lazily on the first stream that needs it); for a database asset, the database side builds it when it opens a driver session (`extdriver`, below), with `Ops` fixed to the host calls a driver needs. A restricted driver scope is therefore an attribute of the scope, not a branch in the runtime.

**Host function surface** (permissions declared in `manifest.json`, enforced at each host call): scoped filesystem read/write, HTTP and TCP as above, host-owned asset connection settings (an asset type declares `connection: {sshTunnel, proxyChain, tls}` in `describe()`; a declared SSH tunnel is the asset's `SSHTunnelID`, a declared proxy chain / TLS is stored under a host-reserved key inside the asset's config JSON — stripped by `pkg/extension.StripHostConnectionConfig` before `ctx.AssetConfig()` and `Plugin.ValidateConfig` hand config to the guest — and applied by the scope the type's declaration produced, via `connpool.ProxyChainDialContext` and `connpool.BuildAssetTLSConfig`, failing rather than falling back to a direct or unverified dial; since `connection` and `auth` apply only to the endpoint, an asset type declaring either is refused at load unless its configSchema marks a `format:"endpoint"` field and the manifest declares `network.assetEndpoint`), host-side credential injection (an asset type declares `auth` bindings in `describe()` — header / query / basic, value templates over its config fields with `{{field}}` / `{{base64(...)}}`, one group picked by a selector field; the scope's `Auth` renders them from the plaintext `extension_svc` decrypts for just the referenced fields, whatever `credentials` says, and `authTransport` applies it per request and per endpoint redirect hop on a clone, so neither the cached client nor anything returned to the guest carries it; a decrypt failure fails the open), asset-config access (credential fields decrypted only with `permissions.credentials: "read"`, which the install confirm and the settings extension detail flag as high risk), KV storage (per-value / per-extension quotas), native file dialogs, logging, and tool events / cancellation (`tool.event`, `tool.should_stop`). A plugin keeps a small pool of live instances (4 by default, recycled every 512 calls), so calls into one extension run concurrently; IO handles and cancellation are scoped to a single invocation, not to the plugin. A tool call's timeout is the tool's declared one (default 30s, at most 10 minutes, none for a `noTimeout` page-only tool); `check_policy`, config validation, test connection and `describe` carry the 30s ceiling.

**Database drivers** are a contribution like the rest, but their session is not a tool call. `internal/extreg/dbdrivers.go` attaches each manifest-declared driver to the driver registry (`internal/dbdriver`) as an `extensionDriver` (`dbdriver.go`); `internal/extreg/extdriver` (`extdriver.New(plugin)`, `Drivers.OpenDriverSession` / `Drivers.ClassifyStatements`) holds the host side of the session, which forwards every `dbdriver.Session` operation to the guest as JSON (`pkg/extwire/driver.go`) over up to three instances leased with `Plugin.Lease`, each bound to the scope `extdriver` builds from the open request (the asset's `host:port` as its endpoint, the transport as its route, the Kerberos ticket source, a fixed `Ops` list). Details and the extension author's side: [Adding a database driver](references/adding-a-database-driver.md#provided-by-an-extension).

**Descriptor cache.** `describe()` runs once per load, then is cached in the `extension_describe` table (`internal/repository/extension_describe_repo`, wired to `pkg/extension`'s `DescribeCache` seam in `internal/bootstrap`) keyed by the wasm binary's SHA-256. Listing extensions, showing a disabled one, and resolving which extension owns an asset type from `opsctl` all read that cache instead of compiling and running a module; a rebuilt binary changes the hash and is described again, and an answer that no longer parses is discarded, so a wire-format change needs no migration. A cached answer goes through the same contribution-point `Check` as a fresh one (`LoadManifestInfo`, `Manager.describeInto`), so the desktop app, the list and opsctl reach the same verdict. When `opsctl` boots and an enabled extension has no cached answer (the desktop app never loaded it on this machine), it loads that extension once itself, which writes the cache; a disabled extension is never loaded. The cached path compiles nothing, and attaches contributions without a running guest (`ExtensionView.Plugin()` is nil).

**Test connection.** An asset type registers `opskat.AssetType[C](...).TestConnection(fn)` in the guest; `describe()` reports it as `AssetTypeDef.TestConnection`, and the asset form shows its "Test connection" button only then. The button reuses the same `System.TestAssetConnection` IPC entry point and `internal/service/conntest` dispatch table every built-in type's tester registers into — `internal/extreg`, loading the extension, builds the tester through a `ConnTestRegistrar` injected by the process that runs the extension (`extension_svc.Service.ConnTestRegistrar`, wired from `main.go` and by opsctl when it activates an extension; `internal/extreg` cannot depend on it directly — `extension_svc` already depends on `extreg`, so the reverse edge would cycle) and registers it under the asset type, exactly like `ssh.go` / `query.go` register their own. The tester merges any password field the form's submitted config leaves out with the edited asset's stored, decrypted value (a new asset has nothing stored, so an omitted field there just decodes to the guest's zero value), keeps that merged plaintext for host-side credential injection only (`AdHocAssetConfig.Credentials`), gates the guest's copy behind the extension's `permissions.credentials` the same way `ctx.AssetConfig()` would, and calls `Plugin.TestConnection`, which runs `fn` against an **ad-hoc** asset (`extension.AdHocAssetConfig`) rather than a database row — the values under test are exactly the ones the caller is about to save, or never will. `fn` reaches the endpoint through the same host IO `network.assetEndpoint` gates, with a scope resolved from the ad-hoc config instead of storage; it never goes through policy, since testing a connection is not an operation on the asset.

**Lifecycle:** `internal/service/extension_svc` scans the extensions dir at startup, applies enabled/disabled state from `extension_state_repo`, and loads each enabled extension through the contribution registry; KV data is persisted via `extension_data_repo` and `describe()` answers via `extension_describe_repo`. Enable / disable / install / uninstall drive the same path and persist state. An installed extension the host refuses is not skipped: the list shows it with its reason (`ExtensionInfo.LoadError`, kind `incompatible` for a `hostABI` this app does not support — naming the declared and supported versions — or `invalid` for a manifest or `describe()` answer that failed to parse or check), and `opsctl exec` on an asset it provides names the extension and the reason instead of loading it. Install confirmation (`extension_svc.InstallConfirm`) lists every permission and driver id as a `CapabilityGrant`; `credentials: "read"`, `network.assetRoute` and `permissions.kerberos` carry `HighRisk`, and an upgrade marks the grants it adds as new. The desktop dialog and `opsctl ext dev` render the same list.

**Official store.** Three pieces, split by what they know. `pkg/extstore` is the I/O-free index model shared with the publisher in the extensions repo: `ParseIndex` (format version checked first — an unknown format is an `*UnsupportedFormatError`), `Verify` / `Sign` (ed25519 over the raw `index.json` bytes, `.sig` = standard base64, any one of several trusted keys accepted so the key can rotate) and `SelectInstallable` (newest version passing `extmanifest.CheckCompatible` whose source type this build fetches, never below the installed one; a version whose `hostABI` this app does not support is not installable). `internal/service/extstore_svc` is the app side: `Refresh` downloads `index.json` + `index.json.sig` from the extensions repo's `main` through the app's download mirror (`update_svc.ApplyMirror`), size-bounded, verifies against the embedded trusted keys (`trusted_keys.go` — an empty list fails every index as "signature invalid", never "trust anything"), parses and caches the result; `StoreIndex()` returns the last verified index, `State(lang)` the store cards, and failures are typed by kind (fetch / signature / format / invalid). It also owns `PullRegistry()`, the one place package pulls must resolve their registry — the "Extension downloads" setting (`bootstrap.ExtensionRegistry`: a host, optionally followed by the repository path a mirror keeps the upstream registry under, e.g. `mirror.example.com/ghcr.io`, which becomes `ociclient.Registry.Prefix` and is prepended to the repository as `docker pull` would), always over https; only the `OPSKAT_E2E_EXT_REGISTRY=http://…` override below selects plain http (`ociclient.Registry.PlainHTTP`). In an `OPSKAT_E2E=1` run only, `OPSKAT_E2E_EXT_INDEX_URL` / `OPSKAT_E2E_EXT_INDEX_KEYS` / `OPSKAT_E2E_EXT_REGISTRY` replace the index URL, trusted keys and registry host so verification never depends on the published index. The extension binder exposes it as `ListStore(lang)` (cached, no fetch) / `RefreshStore(lang)` (fetch, failure returned in the state), rendered by Settings → Extensions → Store (`frontend/src/components/settings/ExtensionStore.tsx`). `opsctl ext search` / `ext install` / `ext update [<name> | --all]` reach the same store through the running app over `approval.sock` (request types `ext_store_search` — read-only, `extstore_svc.List`, refreshing first when no index has verified — and `ext_store_install`, handled in `internal/app/opsctl/ext_store.go`): an install raises the window and runs `InstallFromStore` (`internal/app/extension/store_install.go`), so the app's own install confirm is the approval (no extra opsctl dialog), and `--all` sends one request, hence one confirm, per updatable extension. `internal/pkg/ociclient` is the anonymous OCI pull client for packages: registry auth challenge → anonymous token → manifest → the single layer, aborted past the expected size or once the registry has sent nothing for a minute (a stalled mirror fails as a network error instead of hanging the install), and deleted on a sha256 mismatch, with errors classified network / auth / registry protocol / size / digest. Both the index fetch and the package pull send through `netproxy.Transport()` (see [§4](#4-process-wiring-maingo)), so they follow the network proxy setting; a proxy-side failure surfaces as the same fetch / network error, with the proxy still visible in its text.

**What `internal/extreg` wires.** For one loaded extension, the points above attach, into the app-wide registries the built-in asset types use: an `assettype.AssetTypeHandler` derived from the asset type's `configSchema`; a `permission` executor + `CanonicalizeFunc` + `PolicyCheckFunc` for its asset type; its `SKILL.md` plus a tool/parameter reference rendered from the policy tools' parameters as the `help` document (page-only tools are left out); its `ext:` policy groups; and its database drivers. Attaching is all-or-nothing and **refuses an asset type another extension or a built-in type already owns** — asset type → extension is one-to-one because `exec` dispatches through it. Revoking removes every one of those entries. `opsctl` is a separate, short-lived process, so at startup it attaches each **enabled** extension from the descriptor cache without a guest (`extension.ScanInstalledDir`, the same scan `Manager.ScanInstalled` runs for the desktop list): the asset type, the `help` document, the `ext:` rule landing and the driver descriptors register locally; the executor, the policy check and driver sessions do not — they would have to call the guest. So `opsctl create` / `help` / `policy` resolve extension types locally, and `opsctl exec` on an extension asset activates only that asset's extension in opsctl's own process (`extension_svc.Service.Activate`: load its WASM, replace the guest-less attach with a full one) and runs the command through the same approval → unified `exec` handler path a built-in type takes — whether or not the desktop app is running, which at most acts as the approver. Its host functions are the desktop's minus the window: `Service.HostConfig` supplies asset config and credentials, KV and the asset connection path (an SSH hop on it that asks for MFA is answered from the same sources, in the same order, as `opsctl exec` on an SSH asset — opsctl registers its responder with `credential_resolver.WithConnectionPathMFA`, which `ResolveProxyChain` hands to every SSH hop layer; with no source the command ends in `NEEDS MFA`, exit code 3), a file-dialog request fails pointing at the tool's `--<flag>-file` parameter, and a disabled extension is refused without being loaded. `opsctl ssh` / `exec` / `cp` / `batch` on SSH assets register their responder with `WithMFA` instead, which `DialAssetSSH` passes on to the target's own connection path, so built-in non-SSH types dialing through a tunnel (a database item in `batch`, an object-storage endpoint in `cp`) leave such a hop unanswered. The frontend mirrors this: `frontend/src/extension/assetTypes.ts` turns the same `extreg.Manifest` — which it receives from the backend, never parsing `manifest.json` itself — into an `AssetTypeDefinition` in the shared asset-type registry, so no UI surface branches on "is this an extension type". Pages are loaded by `frontend/src/extension/loader.ts`, which injects `window.__OPSKAT_EXT__` (`React`, `ReactDOM`, `i18n`, `ui`, `hostUI`, `api`) from `frontend/src/extension/inject.ts`; `hostUI` exports `version` (`"1.0"`, kept equal to `HostABIVersion` by `TestHostUIVersionMirrorsHostABI`) and the three wrapper components `CodeEditor`, `JsonTreeView` and `DataTable` whose props `frontend/src/extension/hostui/` owns, so the host's internal components can change without breaking pages; a page's slot (today `asset.connect`) is validated at load.

**Extension development** has no second host. `opsctl ext dev <dir>` sends an unpacked extension directory to the running app over `approval.sock` (request type `ext_dev_install`, handled in `internal/app/opsctl`), which installs it through the same `extension_svc.Install` the "install from directory" button uses — so a dev build loads through exactly one path, with the same permission enforcement and registries as a shipped one. Re-running the command after a build is the reload; `Install` stages the new build in a scratch directory and loads, describes and attaches it there; only on success does it swap it in atomically and notify the frontend — a broken build leaves the previous version installed, loaded and attached. Because it installs and enables unreviewed WASM with whatever permissions its manifest declares, every install is confirmed by the user in the existing opsctl approval dialog — it is `Install`'s confirm, rendering the same `InstallConfirm` the desktop dialog gets (source directory, name/version, permissions with the high-risk ones marked and the added ones marked new, overwrite of an installed extension); the confirmed snapshot is what gets installed, and the commit is refused if the installed version changed after it was confirmed, and a confirmation is remembered in memory for the same directory + extension + permissions until the app exits, so the rebuild-reload loop does not re-prompt. Point `--data-dir` at the verification sandbox ([VERIFICATION.md](VERIFICATION.md)).

## 8. opsctl & the multi-process flow

`opsctl` performs asset operations headlessly and dials its own connections; the desktop app is the broker for approvals only. It shares the same bootstrap (DB, credentials) and talks to the running app over one local IPC endpoint, authenticated with a token file written at startup. `internal/localipc` maps the logical socket paths to user-restricted named pipes on Windows; macOS/Linux retain Unix sockets under the data dir with mode 0600. See [Windows local IPC](references/windows-local-ipc.md) for endpoint identity, permissions, the both-binaries upgrade requirement and the manual AF_UNIX probe:

- **`approval.sock`** (`internal/approval`, server started from `internal/app/opsctl`) — line-delimited JSON request/response. When a command needs confirmation, opsctl sends an `ApprovalRequest` (exec / cp / create / update / delete / batch / ext_dev_install, plus the extension store's read-only `ext_store_search` and `ext_store_install`, whose confirm is the app's own install dialog — see [§7](#7-extensions--wasm-plugins)); the app emits a Wails event, the UI shows the dialog, and the decision (plus any user-edited grant patterns) is returned. Approved **grants** are persisted via `grant_repo` so later matching commands are auto-approved.

`internal/sshpool` pools live SSH clients (ref-counted, idle-reaped). `internal/pkg/proxychain` composes ordered SSH, SOCKS5, and HTTP-script layers; `credential_resolver.ResolveProxyChain` resolves referenced SSH assets and secrets once — when the first hop is an SSH asset it is reached through that asset's own connection path (its proxy chain, or its SSH-tunnel / SOCKS5 fields), expanded recursively with a depth limit, while every later hop is dialed from the hop before it — and stamps each SSH / SOCKS5 layer with the SSH dial-timeout tuning (`internal/pkg/sshtuning`) as the limit for each step of bringing that layer up (handshake, opening the channel to the next address); `internal/connpool.ProxyChainDialContext` adapts the result for protocol and HTTP transports. Database, Redis, MongoDB, Kafka (brokers plus Schema Registry and Connect), etcd, RDP, Kubernetes, and the cached S3-compatible clients use that path. Local SQLite does not; remote SQLite VFS accesses its file through the selected pooled SSH asset, so that SSH asset owns the network chain. The RDP app service streams framebuffer dirty regions, pointer/input events, and clipboard text/files over Wails events; the VNC app service composes the same proxy chain but dials the RFB endpoint directly from `vnc_svc` and bridges the raw RFB byte stream to the in-app noVNC client over Wails events (with an optional SSH/SFTP file channel); the OSS app/service exposes the built-in bucket/object browser, transfer queue, copy/move/delete, previews, and presigned URLs over Wails IPC. A presigned URL opened by an external browser does not inherit the app's in-process proxy chain. RDP and VNC have no built-in policy kind and no opsctl operation command. Object storage now has both: `PolicyKindOSS` carries bucket/object semantics (see [§6](#6-ai-subsystem)), and it reaches opsctl through the shared `exec` verb rather than a dedicated one. opsctl resolves credentials and dials through `credential_resolver` itself, and runs its policy/grant check locally, whether or not the app is running. A NeedConfirm first picks an approver (in `cmd/opsctl/command`): an interactive terminal (stdin and stderr both TTYs) prompts right there, where "allow always" writes a permanent rule through the same write path as `opsctl policy allow`; then the desktop dialog over `approval.sock`; with neither available opsctl refuses with exit code 3 and a fixed stderr marker — `NEEDS AUTHORIZATION` (with a paste-ready `opsctl policy allow` line) for subjects a rule could match, `NEEDS TTY` for `create`/`update`/`delete`, the `policy` write subcommands, and shell commands the policy cannot split into sub-commands (the parse error printed as `Reason:`), which no rule can pre-authorize and only a human in a terminal may perform or approve.

End to end — `opsctl exec <asset> -- <cmd>`: resolve asset → local policy check → if NeedConfirm, pick the approver (terminal prompt when interactive, desktop dialog over `approval.sock` otherwise, structured refusal with exit code 3 when neither) → on approval, dial the asset and execute → stream stdout/stderr/exit, write the audit log. The desktop app's lifetime never affects a command already running.

Asset automation has two shared service boundaries. `internal/service/asset_put_svc` consumes the selected `assettype.AutomationContract`: it rejects undeclared config fields, applies type-owned normalization, validates referenced credentials or SSH Agent associations, and exposes only safe approval/audit views. `Prepare` is side-effect-free; `Commit` encrypts supported plaintext in the asset through its type handler or binds an already-existing credential reference, then writes the asset in one transaction. Asset creation never creates a managed credential; SSH private-key material is not an automation input and callers must create an SSH-key credential in the desktop key manager before passing `credential_id`. AI `put_asset` calls this same boundary directly. `internal/service/credential_query_svc` is the shared read boundary for AI and opsctl: typed refs (`credential:<id>` / `agent-source:<id>`) produce password/SSH-key/Agent metadata, usage and bounded runtime status without secret or Agent endpoint disclosure; `get_asset` asks the registered type owner for an authentication association and enriches only that one detail response.

End to end — `opsctl create asset`: parse generic `--config` or `--config-file` and explicitly supplied compatibility flags → resolve files, SSH asset references and credential/Agent inputs → call `asset_put_svc.Prepare` so unknown fields, defaults, auth conflicts and references are checked before approval → send the safe detail over `approval.sock` → on approval call `asset_put_svc.Commit` for the asset transaction → notify the desktop, write the producer-owned Audit projection (`SafeAuditArgsForResult` field allowlist): ordinary config and identity plus any typed credential reference are retained, write-only secret fields are absent — no generic redactor — and print the safe ID/authentication result. Denial or any prepare/commit failure leaves no new asset row.

## 9. Frontend

`frontend/` is a **pnpm workspace** (Vite 6, Tailwind 4, shadcn/ui over Radix, Zustand 5). The root app lives in `frontend/src/`; `frontend/packages/ui` is the shared `@opskat/ui` component library.

- **No React Router.** Navigation is a custom tab system in `tabStore`; tab kinds are the `TabType` union `"terminal" | "ai" | "query" | "page" | "info" | "editor"`, each with its own metadata. Tab state persists to localStorage for session restore.
- **One Zustand store per domain** in `frontend/src/stores/` (enumerate with `git ls-files 'frontend/src/stores/*.ts'`). Components depend on stores/hooks, not on sibling components' internals; shared domain state and selectors live in stores. A stateful pane may own its view-local IPC/event lifecycle when that lifecycle is not shared, as `RDPPanel` and `VNCPanel` do for one mounted RDP or VNC session.
- **Database drivers:** the query panel and the database asset form take everything driver-specific from the descriptors returned by `Query.ListDatabaseDrivers` (`frontend/src/lib/dbDrivers/`: `useDatabaseDrivers`, `driverHasCapability`, `driverUsesField`, `registerDriverFormField`), not from driver-name checks; an ESLint rule rejects driver-name comparisons outside that directory and test files.
- **Backend bridge:** the generated, gitignored `frontend/wailsjs/go/<domain>/*` bindings call into the matching `internal/app/<domain>` binder; backend→frontend push uses `EventsOn` / `EventsOff` against events the app emits.
- **i18n:** i18next with locales `frontend/src/i18n/locales/{zh-CN,en}/common.json`, single namespace `common`, keys via `t("key.subkey")`.
- **Tests:** Vitest + happy-dom + React Testing Library; the Wails runtime and bindings are mocked in `frontend/src/__tests__/setup.ts`.
