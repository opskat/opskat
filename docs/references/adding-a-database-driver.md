# Adding a Database Driver

> This guide is the concrete how-to for adding a driver to the `database` asset type (MySQL, PostgreSQL, SQL Server and SQLite are the built-in ones): which interfaces to implement, what the descriptor declares, what the session contract requires, how the conformance test and the fake driver prove it, how the frontend follows the descriptor, and which files still branch on a driver name this round.
>
> Engineering principles (SOLID, Reuse first, the Fix policy) live in [`../AGENTS.md`](../../AGENTS.md); the architecture and subsystem map live in [`../ARCHITECTURE.md`](../ARCHITECTURE.md). Adding the asset type itself is a different path: see [`./adding-an-asset-type.md`](./adding-an-asset-type.md). Before editing this file, read [`../DOC-MAINTENANCE.md`](../DOC-MAINTENANCE.md).

## Core Idea: Register a Driver, Do Not Branch on Its Name

Everything that differs between SQL databases lives behind one registry, `internal/dbdriver`. A driver registers one `Driver` implementation (which carries its `Descriptor`); shared code looks the driver up by the id stored in the asset's `DatabaseConfig.Driver` and calls through it. The contract itself is public: `pkg/dbdriver` (package `dbdriver`) holds `Driver`, `Descriptor`, `Session`, the request and result types and `Config`, and `pkg/dbdriver/sqldb` the shared `database/sql` session. Neither imports an `internal/` package and both build for `GOOS=wasip1` (`TestPublicDriverContractStandsAlone` in `internal/archtest`), so an extension can implement the same contract; the registry and the built-in dialects stay in `internal/`. Do not add `if cfg.Driver == ...` or `switch driver` to shared Go or TypeScript code; the guards described in [Guards](#guards-against-regressing-to-name-branches) fail the build when you do.

- Backend registry: `internal/dbdriver` (`Register` for built-ins, `TryRegister` / `Unregister` for drivers an extension provides, `Lookup`, `ByName`, `List`, `IDs`, `LocalizedDescriptor`). Its package name is also `dbdriver`, so code that needs both imports the registry as `dbregistry`. An id that is not registered yields `dbregistry.ErrDriverUnavailable`, which names the driver. Nothing falls back to MySQL. The asset itself stays editable and deletable: saving it skips the driver-owned config rules (the driver-independent ones still apply), and an AI / opsctl update that carries no connection config leaves the stored config as it is, while one that does is refused with the same error.
- Frontend: `frontend/src/lib/dbDrivers/`. The `Query.ListDatabaseDrivers(lang)` binding (`internal/app/query/drivers.go`) returns every registered `Descriptor`, ordered by `Descriptor.Order`, with an extension driver's own field labels translated into `lang`; the frontend reads the driver dropdown, form fields, icon, default port, schema grouping and which entry points to show from it.

Enumerate the built-in drivers from committed code rather than copying a list into prose:

```bash
git ls-files 'internal/dbdriver/*/*.go' | grep -v '_test.go'
git grep -n "Register(" -- internal/dbdriver/mysql internal/dbdriver/postgresql internal/dbdriver/mssql internal/dbdriver/sqlite
```

## Backend Steps

### 1. Create the package

Add `internal/dbdriver/<name>/` (the built-ins are `mysql`, `postgresql`, `mssql`, `sqlite`). The driver package may import the contract `pkg/dbdriver`, `pkg/dbdriver/sqldb`, the registry `internal/dbdriver` (to `Register`) and the entity layer; it must not import `internal/assettype`, because `assettype` links the drivers in (see step 5) and the import would cycle.

### 2. Declare the descriptor

`dbdriver.Descriptor` is plain, serializable data that is handed to the frontend as is:

| Field | Meaning |
| --- | --- |
| `ID` | The value stored in `DatabaseConfig.Driver`. Renaming it is a data migration. Lowercase word, `^[a-z][a-z0-9_]*$` |
| `Name` | Display name (a proper noun, not translated) |
| `Icon` | Asset icon name |
| `Order` | Display order, positive, small first. The built-ins use 10 / 20 / 30 / 40; the dropdown and the driver lists in error and help text follow it |
| `Aliases` | Extra names accepted by `--type` assertions (`postgres`, `sqlserver`, `sqlite3`); an empty slice, not `nil`, when there are none. The `id` is always accepted |
| `DefaultPort` | Default port; `0` for drivers without a port field. Declared if and only if the form uses `FieldPort` |
| `Form` | Per tab (`TabConnection`, `TabTunnel`, `TabTLS`, `TabAdvanced`) the fields the driver uses, in display order. A tab with no declared field is not shown |
| `Capabilities` | The features the driver supports; each is declared separately, undeclared means unsupported |
| `CanDisableForeignKeyChecks` | A detail of `CapImport` (declare it only together with it): the session can switch foreign key checks off for an import batch and back on afterwards (`BatchRequest.DisableForeignKeyChecks`). Without it the import dialog does not offer "ignore foreign keys" and the session refuses the request with `ErrUnsupported`. MySQL, SQL Server and SQLite declare it; PostgreSQL does not |
| `LocatesRowWithoutPrimaryKey` | A detail of `CapGridEdit` (declare it only together with it): on a table without a primary key the session's grid-edit statements still change / delete exactly the one row the user picked, not just one of the rows with the same values (PostgreSQL `(tableoid, ctid)`, since `ctid` alone repeats across partitions and inheritance children; SQLite `rowid`; in `sqldb` the dialect's `RowEditor.ExactRow`). Without it the grid shows the "no primary key (full-row match)" hint. PostgreSQL and SQLite declare it; MySQL and SQL Server do not |
| `CreateDatabaseOptions` | A detail of `CapCreateDatabase` (declare it only together with it): the option fields the create-database dialog shows, each `{Key, Default}` in dialog order, with `Key` one of `dbdriver.OptionCharset` / `OptionCollation`. The dialog shows exactly these fields with these defaults and the session refuses options it did not declare. MySQL: charset `utf8mb4`, collation `utf8mb4_0900_ai_ci`; PostgreSQL: encoding `UTF8`, collation default empty (an empty collation writes no `LC_COLLATE` / `LC_CTYPE`, so the template database's applies); SQL Server: collation only, default empty (no charset field); SQLite has no create database |
| `AlterTableAttributes` | A detail of `CapAlterTable` (declare it only together with it): what the alter-table dialog may change besides renaming the table, renaming / adding / dropping columns (always allowed with `CapAlterTable`). Values are `dbdriver.AlterAttribute`s: `AlterTableComment`, `AlterColumnType` / `AlterColumnNullable` / `AlterColumnDefault` (of existing columns; a new column always takes all three) and `AlterColumnComment` (new and existing columns). The dialog locks the inputs of undeclared attributes and the session refuses a request that changes them with `ErrUnsupported`. MySQL and PostgreSQL declare all five; SQL Server only column type and nullability; SQLite none (an empty list) |

Form fields are `FieldHost`, `FieldPort`, `FieldUsername`, `FieldPassword`, `FieldDatabase`, `FieldSQLiteSource`, `FieldPath`, `FieldSSHAsset`, `FieldTunnel`, `FieldSSLMode`, `FieldTLS`, `FieldTLSCert`, `FieldParams`, `FieldReadOnly`, `FieldQueryTimeout`. `FieldTLSCert` is the certificate field group (like `FieldTunnel`, a group rather than one config key): the enable switch `tls`, `tls_insecure`, `tls_server_name` and the CA / client certificate / client key each as a file path or pasted content (`tls_{ca,cert,key}_{file,pem}`), the same keys and meaning as a Redis asset, the pasted key stored encrypted. `Descriptor.Validate` only accepts it on `TabTLS` and not together with `FieldTLS` (the group has its own switch). No built-in driver declares it — their `tls` / `ssl_mode` keep their own meaning; an extension driver that does needs host ABI `2.4` (see [Provided by an Extension](#provided-by-an-extension)). Declaring `FieldPassword` is also what tells the automation layer that the driver authenticates with a password (`password` / `credential_id` are rejected otherwise). The shared connection arguments (tunnel, proxy chain, credential, `read_only`, `query_timeout_seconds`) are handled once by the database asset handler (`internal/assettype/database.go`, `connection_args.go`); a driver only owns the fields specific to it.

Capabilities (`dbdriver.Capabilities()` is the full list): `CapSchemas` (group by schema under a database), `CapCreateDatabase`, `CapViewDDL`, the four object kinds `CapViews` / `CapProcedures` / `CapFunctions` / `CapTriggers`, and the write-path entries `CapGridEdit`, `CapCreateTable`, `CapAlterTable`, `CapDropTable`, `CapTruncateTable`, `CapImport`, `CapExportSQL`, `CapCopySQL`, plus `CapReadOnly` (connection-level read-only). See [Write path](#write-path-what-still-needs-shared-edits) before declaring any of the write-path ones.

### 3. Implement the config rules

`dbdriver.ConfigRules`: `ValidateConfig` (before persisting), `CreateDefaults`, `ValidateCreateArgs`, `ApplyCreateArgs`, `ApplyUpdateArgs` and `ConnectionView` (what opsctl / AI show about the asset). The rules work on `dbdriver.Config`, the driver's view of the asset config: every field of `asset_entity.DatabaseConfig` except the password, the credential and the proxies, which the host resolves itself. The entity converts once at the boundary (`DatabaseConfig.DriverConfig` / `SetDriverConfig`); `ValidateConfig` additionally gets a `dbdriver.Route` saying whether the asset has an SSH tunnel, a SOCKS5 proxy or a proxy chain with layers. Arguments arrive through `dbdriver.Args`, which wraps the shared `Arg*` helpers; do not re-parse the raw map. Host-and-port drivers embed `dbdriver.NetworkRules{DefaultPort: ...}` and get all six (the built-in MySQL, PostgreSQL and SQL Server do); SQLite implements its own.

Rules the entity layer cannot import are reached through the hook `asset_entity.SetDatabaseDriverConfigValidator`, which `internal/dbdriver/registry.go` installs; you do not touch the entity layer.

### 4. Implement the connector and the session

`dbdriver.Connector` is `Open(ctx, OpenRequest) (Session, error)` plus `SessionPerDatabase() bool`.

- `OpenRequest` carries the `Config`, the already-decrypted `Password`, and a `Transport`. The shared code has resolved tunnels, proxies, proxy chains and `.local` handling already: every network connection the driver makes must go through `Transport.Dial` when it is non-nil (through an SSH tunnel it always reaches the asset's `host:port`, whatever address the driver passes); a driver whose database is a file on a remote host opens it through `Transport.RemoteFS`. `Transport.DialAddr` (the same route to the address asked for) and `Transport.Direct` serve the extension reach gate below, and `AssetID` only names the asset in host logs; built-in drivers ignore them. `OpenRequest.TLS` (`*TLSMaterial`) is set only for a driver whose form declares `FieldTLSCert`, and only when the asset has `tls` on (`connpool.OpenDatabase`, `driverTLS`): skip-verify, server name, and the CA, client certificate and client key contents — paths read by the process opening the session (desktop or opsctl), the stored key decrypted — handed like the password, only to open and never logged. A file that cannot be read or a key that does not decrypt fails the open naming the field, not its content; whether the contents are valid is the driver's own TLS to judge, with its own error. With `tls` off, or a driver that does not declare the group (every built-in), it is `nil`. The driver never reads `Proxy` / `ProxyChain` / `SSHAssetID` itself.
- `Open` returns only after the database is reachable. A config that asks for `ReadOnly` must be honored; a driver that does not declare `CapReadOnly` must reject it with `dbdriver.ErrUnsupported` rather than open a writable session.
- `SessionPerDatabase()`: `true` when the database name is part of the connection (one session per asset and database); `false` when one session covers the whole asset and the database name is only a namespace in it (SQLite). Shared code decides the granularity of session reuse from this and does not look at the driver name.

`dbdriver.Session` is what shared code holds. It must be safe for concurrent use. Everything returns structured results; shared code never builds dialect SQL and never touches the driver's connection:

| Group | Methods |
| --- | --- |
| Execution (required) | `Execute`, `ExecutePaged` (one page plus the total in `RowSet.Total`) |
| Tree browsing | `ListDatabases`, `ListTables`, `TableMetadata`, `ListObjects`, `ObjectSource` |
| Table browsing | `OpenTable`, `TableRows`, `CountTableRows`, `StreamTableRows` (structured `FilterItem` / `SortItem`, no SQL text) |
| Text output | `TableDDL`, `StarterQuery` |
| Write-path statements | `PrepareRowStatements` (copy / export as SQL: reads what generating needs — column types, session-dependent literal rules — and returns a `RowStatementWriter` whose `RowStatements` gives one `INSERT`, or one single-row `UPDATE`, per row of a `RowStatementsRequest` without touching the database again, so whole-table export can generate while its read cursor holds the session's only connection), `GridEditStatements` (grid editing: one `INSERT` per new row, one single-row `UPDATE` per edited row located by its original values, one single-row `DELETE` per deleted row of a `GridEditRequest`, returned as three lists in request order), `CreateTableStatements` (a `CreateTableRequest`: name and columns), `DropTableStatements`, `TruncateTableStatements` (SQLite writes `DELETE FROM`), `CreateDatabaseStatements` (a `CreateDatabaseRequest`: name and the options the driver declares); generated, never executed |
| Batch execution | `ExecuteBatch` (import: a `BatchRequest`'s statements in order on one connection, see below) |
| Lifecycle | `Close` |

Anything the driver does not provide returns an error wrapping `dbdriver.ErrUnsupported` and runs no statement. `Execute` and `ExecutePaged` must always work.

`ExecuteBatch(ctx, BatchRequest{Statements, Atomic, ContinueOnError, DisableForeignKeyChecks, Database, Table}) (*BatchResult, error)` runs a whole import batch on one connection, skipping blank statements. `Atomic` puts it in one transaction that stops and rolls back at the first failure; otherwise each statement commits on its own and `ContinueOnError` decides whether to go on after a failure. With `DisableForeignKeyChecks` the driver switches foreign key checks off before the batch (outside the transaction, on the same connection) and back on afterwards, also after a failure, a rollback or a cancelled `ctx`; `Table` is the import target, which drivers that disable constraints per table (SQL Server) act on. A failed statement is recorded in `BatchResult.Executed` (`Index`, `AffectedRows`, `Error`) and is not an error; `RolledBack` reports a rolled-back atomic batch. A failure of the batch itself (no connection, switching foreign key checks, begin / commit / rollback, a cancelled `ctx`) is returned as the error, together with the result so far when statements already ran. The shared import service (`query_svc.RunTableImportBatch`) turns the result into the added / updated / deleted / error counts the dialog shows.

Table names reach the session in the form `ListTables` gives them. A driver that groups by schema (`CapSchemas`) splits `schema.table` at the **first** dot only, so a table whose own name contains dots (`public.a.b`) is one name in browsing and in every generated statement; other drivers treat the whole name as the table name. Write-path statements write literals in the driver's own dialect and may look up the table's column types on the session first: SQL Server prefixes Unicode text columns (`nchar` / `nvarchar` / `ntext`) with `N`, binary columns are hex literals (`0x…`, `'\x…'::bytea`, `X'…'`; MySQL writes only the bytes an import decoded as `X'…'` and keeps text in binary columns a quoted string, as before — `sqldb.Literals.BinaryBytesOnly`), MySQL doubles backslashes unless the session's `sql_mode` has `NO_BACKSLASH_ESCAPES`; every other value stays a quoted string as the grid shows it. Defaults and comments in create / alter table are not values written into the table: they keep the old rule, a plain quoted string with `'` doubled (`sqldb.DefinitionLiterals`). Grid edits locate a row by its primary key, or by all its original values when the table has none (`LIMIT 1` / `TOP (1)` / `(tableoid, ctid)` / `rowid`); a new row with no value is the dialect's all-defaults insert (`() VALUES ()` / `DEFAULT VALUES`); a value the user typed into an identity column is written as given (SQL Server wraps that insert in `SET IDENTITY_INSERT … ON` / `OFF`, also switched off on error, when the target is a user table — into a view it stays a plain insert; PostgreSQL adds `OVERRIDING SYSTEM VALUE` for `GENERATED ALWAYS`). Column names that are not in the table fail the generation.

Drivers on top of `database/sql` should not re-implement the session. `pkg/dbdriver/sqldb` provides `sqldb.NewSession(db, dialect, ...)` and the optional dialect interfaces that switch the groups above on: `sqldb.Dialect` (paging and counting), `sqldb.Catalog` (tree browsing), `sqldb.Tables` (table browsing, quoting, starter query), `sqldb.DDL` (table DDL), `sqldb.RowWriter` (row statements: the dialect's `sqldb.Literals` rules, queried per connection, and its single-row `UPDATE`), `sqldb.TableTruncator` (the truncate statement; create / drop table need only `sqldb.Tables`), `sqldb.DatabaseCreator` (the `CREATE DATABASE` statement and the option keys it accepts; option values are limited to letters, digits, `_`, `.` and `-`, undeclared keys are refused), `sqldb.TableAlterer` (alter table: the attributes it can change, reading the table as the dialog shows it — the name without its schema, the comment, each column's name / type / nullability / default / comment, plus the raw catalog row the dialect keeps for what the dialog does not show — and writing a `sqldb.TableChange` as statements; comparing the request with the current definition and refusing undeclared attributes or unknown columns is shared, and `sqldb.ColumnDefinitionSQL` / `Literals.Default` write a new column), `sqldb.RowEditor` (grid edits, together with `RowWriter`: the insert including the all-defaults and identity forms, the single-row `DELETE`, and `ExactRow`, the physical-row narrowing for tables without a primary key) and `sqldb.ForeignKeyChecks` (the statements that switch foreign key checks off for a batch and back to what they were, worked out on the batch's connection — none at all when a connection-level switch was already off: `SET FOREIGN_KEY_CHECKS`, `PRAGMA foreign_keys`, `ALTER TABLE <target> NOCHECK CONSTRAINT` / `WITH NOCHECK CHECK CONSTRAINT` on just the target's foreign keys that were enabled, re-enabled without re-checking existing rows); a dialect that does not implement one makes the matching `Session` methods return `ErrUnsupported`. `ExecuteBatch` itself (connection pinning, transaction, rollback, restoring the checks) is shared by every `sqldb` session. `sqldb.QuoteSchemaTable` / `sqldb.SplitSchemaTable` give the first-dot table reference for schema-grouping dialects, and `sqldb.Literals.Literal` writes one value for a column type. `sqldb.Establish` pings the database and applies read-only, `sqldb.ParseParams` parses the `params` field, and `sqldb.LimitOffset` is the common paging dialect. The built-in packages are the reference: `internal/dbdriver/mysql/` has `mysql.go` (descriptor and registration), `connect.go` (`Open`, DSN), `catalog.go`, `table.go`, `ddl.go`.

A driver whose session does not wrap a `*sql.DB` at all implements `dbdriver.Session` directly; the fake driver below is the example.

### 5. Register and link

Register in the package's `init()`:

```go
func init() {
	dbregistry.Register(driver{NetworkRules: dbdriver.NetworkRules{DefaultPort: descriptor.DefaultPort}})
}
```

`Register` panics when the id or any alias is already taken by another driver. Then add a blank import of the package to `internal/dbdriver/builtin/builtin.go`; `internal/assettype/database.go` blank-imports `builtin`, so both program entry points (the desktop app and `opsctl`) link the driver. Nothing else in the backend changes: asset validation, `opsctl create asset`, the missing-`driver` error text, `--type` assertions (`internal/ai/permission/type_assert.go` resolves names through the registry), the `exec --help` driver list, test connection, the query panel and AI / opsctl SQL execution all go through `dbdriver.Lookup` / `ByName` / `List`.

## Proving the Driver: Conformance and the Fake

`internal/dbdriver/dbdrivertest` is the test support:

- `dbdrivertest.RunConformance(t, d, newSession)` is the test every registered driver must pass. It checks the descriptor (id and alias format, display name, icon, a declared `Order`, non-nil `Aliases` / `Capabilities`, known tabs / fields / capabilities each used once, default port present exactly when the form has a port field, the `read_only` form field only together with `CapReadOnly`, `CanDisableForeignKeyChecks` only together with `CapImport`, `LocatesRowWithoutPrimaryKey` only together with `CapGridEdit`, `CreateDatabaseOptions` only together with `CapCreateDatabase` and only the known keys `charset` / `collation`, `AlterTableAttributes` only together with `CapAlterTable`, known and each declared once), that the registry resolves the driver by id and alias, that `Execute` and `ExecutePaged` return well-formed results that serialize to JSON, that read-only is refused when `CapReadOnly` is not declared, and that undeclared object types, `GridEditStatements` when `CapGridEdit` is not declared, `ImportStatements` when `CapImport` is not declared, `AlterTableModel` / `AlterTableStatements` when `CapAlterTable` is not declared, create table / drop table / truncate table / create database statements when their capability is not declared (and, when declared, they must return a non-empty statement), `PrepareRowStatements` when neither `CapExportSQL` nor `CapCopySQL` is declared (`Descriptor.GeneratesRowStatements`), and an `ExecuteBatch` that asks to disable foreign key checks when `CanDisableForeignKeyChecks` is not declared, are refused with `ErrUnsupported` without running a statement. `newSession` returns a session without a real database: a stub connection for `database/sql` drivers (`go-sqlmock`), a temporary file for file-based ones. Each built-in package calls it from `connect_test.go`; do the same for yours.
- `RunBrowseConformance` and `RunTableConformance(t, d, newSession, database, table)` check the declared browsing and table operations (`RunTableConformance` also prepares a row-statement writer and generates row statements for the first page when the driver declares export / copy as SQL: one statement per row, an empty list for no rows, and the writer still generates after the session is closed; generates grid-edit statements for the first page when it declares grid editing: one insert / update / delete per row plus an all-defaults insert, three empty lists for an empty request; generates append import statements for the first page (all values `NULL`) when it declares import: one statement per row, an empty list for no rows, and the `OpenTable` column categories name only first-page columns and only the known categories; reads the table for the alter dialog when it declares alter table: the name is the end of the listed name, every column is a column of the first page, and handing the table back unchanged yields an empty statement list and the same table name; and runs `ExecuteBatch` with `dbdrivertest.ConformanceFailingStatement`, disabling foreign key checks when declared: the atomic batch stops at the first failure and rolls back, the continuing one goes past failures, blank statements are skipped, and the checks are restored without error) (including that every `TableMetadata` column serializes `comment` as a string, empty when there is none, and `default` as a string or `null` when the column has no default, so an empty-string default stays distinguishable); they need a session that holds data, so they are run against the fake and against drivers that can provide data.
- Driver-specific SQL text (quoting, paging, filter semantics, DDL) is pinned by tests in the driver package (`catalog_test.go`, `table_test.go`, `ddl_test.go`); `pkg/dbdriver/sqldb/sqldbtest` has a shared filter-semantics suite that each built-in dialect runs.
- `dbdrivertest.NewFake()` is a driver registered only in tests (`dbdrivertest.Register(t, fake)` unregisters it at cleanup). It deliberately has different rules from every built-in (only `host` is required, its own default port and order) and its session is an in-memory table, not a `database/sql` handle. Backend tests that go from asset validation through connection, listing, opening a table and paging via the fake, and frontend tests that fill the driver dropdown and forms from `FAKE_DRIVER` (`frontend/src/__tests__/dbDriverFixtures.ts`), are what show that a new driver needs no shared-code edit. A shared-code change that a fake driver cannot exercise is a sign a name branch crept in.

## Provided by an Extension

A driver can also come from a WASM extension instead of `internal/dbdriver/<name>/`. The contract is the same `pkg/dbdriver`; what differs is where the session runs. The extension author's side (manifest, registration, what `open` is handed) is in [`extensions/README.md` → Providing a database driver](../../extensions/README.md#providing-a-database-driver).

- **Declaration.** The manifest lists the driver ids in `capabilities.databaseDrivers` (host ABI `2.3`), and `describe()` answers one `dbdriver.Descriptor` per id; `pkg/extension` (`descriptor.go`, `manifest.go`) refuses to load an extension whose two lists differ or whose descriptor fails `Descriptor.Validate`. The descriptor's icon is the extension's. On registration (`internal/extreg/dbdriver.go`) the driver gets the network config rules (`dbdriver.NetworkRules`), so its form must declare `host`, `port` and `username` and none of `sqlite_source`, `path`, `ssh_asset_id`; a driver that does not is refused, naming it, and the extension is not loaded.
- **Guest side.** The extension registers `sdkdbdriver.DatabaseDriver(descriptor, open)` (`pkg/extsdk/sdkdbdriver`, a package of its own so that an extension without a driver does not link `database/sql` and `sqldb`; it reaches `describe()` and the call dispatch through `opskat.RegisterDatabaseDriver` in `pkg/extsdk/dbdriver.go`). `open` returns the `*sql.DB` and the `sqldb.Dialect`; the SDK assembles the session with `sqldb.NewSession`, so the dialect interfaces in [step 4](#4-implement-the-connector-and-the-session) decide which operations the session has, exactly as for a built-in `database/sql` driver. The SDK refuses a read-only config with `ErrUnsupported` before calling `open` unless the descriptor declares `CapReadOnly`. `OpenRequest.Transport.Dial` in the guest dials through the host.
- **Host side.** `(*extension.Plugin).OpenDriverSession(ctx, id, OpenRequest)` (`pkg/extension/driver_session.go`) returns a `dbdriver.Session` whose every method is forwarded to the guest as JSON (`pkg/extension/driverwire`). The session runs on up to three module instances of its own (`driverSessionInstances`), outside the plugin's call pool: overlapping operations get one each, later ones wait in arrival order, and a cursor or a batch stays on one instance. Each instance's IO handle table lasts as long as the instance instead of one call: the driver logs in once per instance in `open`, and later operations reuse its connections. A canceled or timed-out call closes that instance's connections and discards it; extra instances close once idle. The guest's TCP connections go through the session's reach gate (`confineReach`): the asset's own `host:port` takes the `OpenRequest.Transport.Dial` the host resolved (direct when it is nil), exactly as a built-in driver's connection does. Any other address is refused, naming it and that the extension does not declare following database redirects, unless the manifest declares `capabilities.network.databaseRedirects` (host ABI `2.4`); then it is dialed with `Transport.DialAddr`, the same route by address — through an SSH tunnel to that address itself (`SSHTunnel.DialAddr`; `Dial` keeps going to the asset's address, since a built-in driver such as MSSQL dials an `ip:port` it resolved locally), its name resolved at the far end of a tunnel, proxy or proxy chain. On a direct route (`Transport.Direct`) the name resolves locally, a loopback, unspecified or link-local target is refused unless the asset's own host is one, and the checked addresses are what is dialed. The first dial of each such address per session is logged with extension, driver, `OpenRequest.AssetID` and address; a failed one returns the route's error naming the address. The config crosses as `dbdriver.Config` (without the host-owned tunnel, proxies and credential) and the decrypted password only in the open call. A refusal crosses with code `unsupported`, so `errors.Is(err, dbdriver.ErrUnsupported)` holds on the host; any other failure is the driver's own message. Numbers in results decode as `json.Number`, so a `BIGINT` keeps its digits. `StreamTableRows` keeps the cursor in the guest and reads it over in batches of 256 rows. A writer from `PrepareRowStatements` generates in the guest, so it keeps the instance alive after the session closes until the writer is garbage collected; the guest then forgets it with the next call on that instance (`driverwire.Call.ReleaseWriters`).
- **Certificate TLS.** A driver whose descriptor declares `FieldTLSCert` makes the extension require host ABI `2.4`: `checkDatabaseDrivers` (`pkg/extension/descriptor.go`) refuses it on an older `hostABI` at load, naming the driver. The `OpenRequest.TLS` the host resolved crosses in the open call (`driverwire.Args.TLS`) to every instance as it logs in, and the SDK hands it to `open` as `OpenRequest.TLS`; the driver builds its own `tls.Config` from it (its database library may start or redo TLS mid-protocol), so nothing falls back to plaintext or skips verification on the host's behalf. The fixture driver declares the group and answers `SHOW OPEN TLS` with what it received.
- **Compatibility.** The JSON is the contract between a host and extensions built at other versions: fields of `driverwire` requests and results may only be added, and both sides ignore fields they do not know.
- **Proof.** `pkg/extension/driver_session_test.go` runs `RunConformance`, `RunBrowseConformance` and `RunTableConformance` against the forwarded session of `pkg/extension/testdata/fixture-dbdriver` (a driver over an in-memory `database/sql` driver), built at test time by `extensiontest.LoadDBDriverFixture`.

## Frontend: Follow the Descriptor

The frontend does not know driver names. `frontend/src/lib/dbDrivers/index.ts` exports:

- `loadDatabaseDrivers()` / `useDatabaseDrivers()` (`loading` / `ready` / `error` states; a failed fetch is shown as an error, there is no built-in substitute list), `findDatabaseDriver(drivers, id)`.
- `driverHasCapability(driver, capability)` and `driverUsesField(driver, field)`: the only way shared components ask whether to show an entry point or a field. When an asset's driver is not registered, the panel shows "driver unavailable" naming it, the asset stays editable and deletable.
- `driverFormGroups` and `registerDriverFormField(field, descs)`: the asset form renders, per tab, the controls registered for the fields the descriptor lists. The shared controls are registered in `genericFields.ts`; SQLite's source switch, file picker and SSH asset selector are registered in `sqliteFields.tsx`. A new driver that reuses existing `FormField` values needs no frontend change; one that needs a control that does not exist yet registers it with `registerDriverFormField`, in `src/lib/dbDrivers/`, not by a branch in the form.

Display names, icons, default ports and schema grouping (`CapSchemas`) come from the descriptor. Structured browsing (`ListDatabases`, `ListTables`, `OpenTable`, `QueryTableRows`, `CountTableRows`, export cursors, `GetTableDDL`, `GetStarterQuery`) the statements for copy / export as SQL (`GetRowStatements`; whole-table export as SQL instead opens the export cursor with `insertColumns`, which prepares the writer before the read and hands over each chunk's `INSERT`s instead of its rows) and for grid editing (`GetGridEditStatements`: the grid's preview, status-bar summary and delete preview show exactly what it returns, and submitting executes exactly those), for create table (`GetCreateTableStatements`), drop and truncate table (`GetDropTableStatements`, `GetTruncateTableStatements`, one call per selected table, each executed against its own database) and create database (`GetCreateDatabaseStatements`), the alter-table dialog (`GetAlterTableModel` loads the table, `GetAlterTableStatements` returns the statements for the edited table and the table's listed name afterwards; the preview shows exactly those and confirming executes them in order, stopping at the first failure) the import statements (`GetImportStatements`: the wizard sends the mapped rows already converted from the source file — text, null, binary bytes as hex — with the target columns, match keys, mode and multi-row options when leaving the mode step; the summary shows the first 8 it returns and starting executes exactly those; how a source value is converted follows the per-column category the driver reports with `OpenTable` as `columnCategories`: number / date / datetime / binary / text) and the import batch (`ExecuteTableImport`, used for copy mode, stop-on-error and ignore-foreign-keys imports) go through the `Query` binder, which calls the driver's session. The import dialog offers "ignore foreign keys" only when the descriptor declares `canDisableForeignKeyChecks`; the grid shows the no-primary-key hint unless it declares `locatesRowWithoutPrimaryKey`; the create-database dialog shows exactly the fields in `createDatabaseOptions` (`{key, default}`, keys `charset` / `collation`) with those defaults, so SQL Server declares only a collation; the alter-table dialog locks what `alterTableAttributes` does not list (`driverCanAlter(driver, attribute)`) and shows its limitation hint for the declared combinations it has text for (none declared, or only column type and nullability). A statement the driver cannot generate shows its error where errors show and nothing is previewed or executed.

## Write Path: Behind the Driver

Every write path is behind the driver: declaring `CapGridEdit` only requires the session's `GridEditStatements`, `CapExportSQL` or `CapCopySQL` its `PrepareRowStatements`, `CapCreateTable` / `CapDropTable` / `CapTruncateTable` / `CapCreateDatabase` their matching `*Statements` method (`CapCreateDatabase` also the descriptor's `CreateDatabaseOptions`), `CapAlterTable` the session's `AlterTableModel` / `AlterTableStatements` (and the descriptor's `AlterTableAttributes`), and `CapImport` the session's `ImportStatements` (every mode's form — upsert, skip, copy's clearing, multi-row chunks — literals, and writing identity columns: SQL Server switches `IDENTITY_INSERT` only when an identity column of a user table is mapped, PostgreSQL adds `OVERRIDING SYSTEM VALUE` for `GENERATED ALWAYS`, and the update modes never set a column the database refuses to update) plus the column categories in `OpenTable`; for `database/sql` drivers that is `sqldb.Importer` (`ColumnCategory`, `ImportInsertSQL`). Import batches run through `ExecuteBatch`. No shared file needs editing for a new driver's writes.

The frontend does not generate write SQL: the session's write methods return the statements and the preview shows, and submitting executes, exactly those. There is no exemption list in either language: no production Go file outside `internal/dbdriver/` and no TypeScript file outside `src/lib/dbDrivers/` and tests may name a driver.

Also outside this seam for now (the spec's out-of-scope list): parsing the AI SQL permission policy per dialect (`internal/ai/policy/query_policy.go` parses with the TiDB parser) and per-dialect keyword completion in the SQL editor. A driver's SQL is checked by the same policy as every other.

## Guards Against Regressing to Name Branches

- Go: `TestNoDriverBranchInSharedCode` in `internal/archtest/driver_branch_test.go` fails on a comparison or `switch` against `asset_entity.DriverMySQL` / `DriverPostgreSQL` / `DriverMSSQL` / `DriverSQLite`, or against a registered driver id or alias string where the other side is a driver value, in any production Go file outside `internal/dbdriver/`. `TestCheckDriverBranch` pins the detection on sample sources (violations reported; driver packages and test files not). There are no exemptions.
- TypeScript: the `no-restricted-syntax` selectors in `frontend/eslint.config.js` reject comparing against a driver-name literal (`===`, `!==`, `==`, `!=`, `case`) under `src/`, except in `src/lib/dbDrivers/` and test files; `frontend/src/__tests__/eslint-harness.test.ts` covers both directions.
- Frontend test fixture: the built-in descriptors that frontend tests feed to `Query.ListDatabaseDrivers` are `frontend/src/__tests__/builtinDbDrivers.json` (loaded as `BUILTIN_DRIVERS` in `dbDriverFixtures.ts`). `TestFrontendBuiltinDriverFixtureMatchesRegistry` in `internal/archtest/driver_fixture_test.go` compares it with the registry and prints the expected JSON when a descriptor changed.
- Hand-written driver lists: `opsctl exec --help` and the missing-`driver` errors are generated from the registry. Two static texts cannot be generated, so `internal/archtest/driver_text_test.go` compares them with the registry (ids, aliases, default ports): `internal/ai/skills/database/SKILL.md` and `plugin/opsctl/skills/opsctl/references/commands.md`. Adding a driver or alias fails those tests until the texts are updated.

## Checklist

1. `internal/dbdriver/<name>/`: descriptor, config rules, `Open` / `SessionPerDatabase`, session (usually `sqldb.NewSession` plus the dialect interfaces), `init()` registration.
2. Blank import in `internal/dbdriver/builtin/builtin.go`.
3. A `connect_test.go` that calls `dbdrivertest.RunConformance`, plus tests for the driver's own SQL text.
4. Declare only the capabilities the driver actually supports: `CapGridEdit` together with `GridEditStatements` (and `LocatesRowWithoutPrimaryKey` only if it narrows to a physical row), `CapExportSQL` / `CapCopySQL` together with `PrepareRowStatements`, `CanDisableForeignKeyChecks` together with the session's way to switch them off (`sqldb.ForeignKeyChecks`), `CapCreateTable` / `CapDropTable` / `CapTruncateTable` / `CapCreateDatabase` together with their `*Statements` method (`sqldb.TableTruncator` / `sqldb.DatabaseCreator`, and `CreateDatabaseOptions` for the dialog's fields), `CapAlterTable` together with `AlterTableModel` / `AlterTableStatements` (`sqldb.TableAlterer`) and `AlterTableAttributes` listing exactly what it can change, `CapImport` together with `ImportStatements` and the column categories (`sqldb.Importer`).
5. A new form field with no existing control: `registerDriverFormField` in `src/lib/dbDrivers/`, and its i18n keys in both locales.
6. Update the driver names in `internal/ai/skills/database/SKILL.md` and `plugin/opsctl/skills/opsctl/references/commands.md`, and the descriptors in `frontend/src/__tests__/builtinDbDrivers.json` (the archtest fails until you do).
7. `go test ./internal/dbdriver/... ./pkg/dbdriver/... ./internal/archtest/...`, then from `frontend/`: `pnpm run lint` and the related vitest files.
